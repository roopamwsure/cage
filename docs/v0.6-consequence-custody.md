# CAGE v0.6 — Consequence Custody

## Purpose

CAGE v0.6 introduces **Consequence Custody**: the controlled boundary between a CAGE Decision and a real-world external system mutation.

v0.5 established whether an intended business consequence should be permitted and how that decision is preserved and proven.

v0.6 addresses the next problem:

> How can a permitted consequence be carried into external execution safely, with constrained authority, while preserving evidence of what actually became effective?

The central separation remains:

```text
Decision != Effect
```

An `ADMITTED` Decision does not mean the consequence was executed.

An execution attempt does not prove that the consequence became effective.

An execution failure does not prove `NO_BIND`.

External reality must be established through authoritative verification before CAGE makes an Effect claim.

---

## Core Principle

A CAGE Decision may make a consequence eligible for custody.

It does not itself execute the consequence.

The v0.6 lineage is:

```text
Action
  |
  v
Consequence
  |
  v
Attempt
  |
  v
Evaluation
  |
  v
Decision
  |
  v
DecisionProof
  |
  v
-----------------------------
     CONSEQUENCE CUSTODY
-----------------------------
  |
  v
ExecutionAttempt
  |
  v
EffectAdapter
  |
  v
External System
  |
  v
AdapterExecutionResult
  |
  v
EffectVerifier
  |
  v
EffectVerificationResult
  |
  v
Effect
  |
  v
EffectProof
  |
  v
Warrant
```

The custody boundary must prevent CAGE from confusing:

```text
permission to attempt execution
```

with:

```text
proof that execution became effective
```

---

## v0.6 Implemented Scope

v0.6 establishes generic, vendor-neutral core contracts for:

- execution-attempt identity;
- custody eligibility;
- exact effect selection for `ADMITTED` and `NARROWED`;
- scoped structural execution authority;
- explicit custody execution orchestration;
- request-level adapter execution observations;
- authoritative effect verification;
- explicit uncertainty;
- reconciliation without re-execution;
- stronger `NO_BIND` semantics;
- EffectProof verification lineage;
- Warrant execution and verification lineage.

v0.6 does not require AWS, Azure, GCP, or any other provider-specific execution model.

---

## Consequence Custody Boundary

Custody begins only after CAGE has produced a Decision.

The custody subsystem consumes existing CAGE lineage. It does not recreate or reinterpret evaluation logic.

Conceptually:

```text
Consequence
    +
Decision
    |
    v
Custody
```

A Decision may permit custody, but custody must never convert:

```text
ADMITTED
```

directly into:

```text
BOUND
```

An Effect is created only from an `EffectVerificationResult`.

---

## Execution Is Explicit

Evaluation never automatically mutates an external system.

Forbidden:

```text
evaluate_attempt()
    |
    v
ADMITTED
    |
    v
automatic external execution
```

Implemented flow:

```text
Decision
    |
    v
ExecutionAttempt
    |
    v
execute_under_custody()
```

This keeps evaluation, replay, proof construction, execution, and reconciliation as distinct operations.

---

## ExecutionAttempt Identity

`ExecutionAttempt` is distinct from the v0.5 evaluation `Attempt`.

An evaluation Attempt represents:

> one evaluation of a Consequence.

An `ExecutionAttempt` represents:

> one identified attempt to carry a Decision into external execution.

Current `ExecutionAttempt` lineage includes:

```text
execution_attempt_id
decision
optional previous_execution_attempt_id
```

The Consequence is derived through the Decision lineage.

Therefore:

```text
evaluation Attempt identity != ExecutionAttempt identity
```

Execution retry semantics may later create another `ExecutionAttempt`, but retry orchestration is not introduced as a new execution feature in v0.6.

---

## Custody Eligibility

Custody eligibility is explicit.

`select_effect_for_custody()` behaves as follows:

```text
ADMITTED
    -> original requested effect

NARROWED
    -> Decision.permitted_effect

HELD
ESCALATED
REFUSED
    -> custody ineligible
```

Ineligible decisions must fail before any adapter invocation.

For `NARROWED`, the broader original requested effect must never reach the adapter.

---

## Scoped Execution Capability

v0.6 models the structural scope of execution authority with `ExecutionCapability`.

Current minimal fields are:

```text
capability_id
consequence_id
action_type
resource_id
```

`validate_capability_for_custody()` requires the capability to match the custody operation on:

```text
same consequence_id
same action_type
same resource_id
```

A capability for another consequence, action type, or resource cannot be reused.

`ExecutionCapability` is deliberately **not** a credential container.

It does not contain:

- OAuth tokens;
- API keys;
- passwords;
- provider credentials;
- AWS role ARNs;
- Azure tokens;
- IAM policies;
- secrets;
- permission documents.

CAGE models execution-authority scope. Provider credential material remains outside generic Core.

---

## EffectAdapter

`EffectAdapter` is the vendor-neutral mutation boundary.

Its current protocol is conceptually:

```python
class EffectAdapter(Protocol):
    def execute(
        self,
        *,
        execution_attempt: ExecutionAttempt,
        effect: RequestedEffect,
        capability: ExecutionCapability,
    ) -> AdapterExecutionResult:
        ...
```

The adapter receives:

- the exact `ExecutionAttempt`;
- the exact selected effect;
- the validated execution capability.

The adapter does not decide whether execution is allowed.

It does not perform CAGE evaluation, IAM policy evaluation, approval workflow logic, or Effect determination.

Its responsibility is to attempt the external mutation and return a request-level execution observation.

---

## AdapterExecutionResult Is Not Effect Truth

The adapter returns `AdapterExecutionResult`.

Current request-level states are:

```text
ACKNOWLEDGED
REJECTED
ERROR
UNKNOWN
```

These states describe what was observed about the execution request.

They do not establish external business reality.

The following mappings are forbidden:

```text
ACKNOWLEDGED != BOUND
REJECTED     != NO_BIND
ERROR        != NO_BIND
UNKNOWN      != EFFECT_UNKNOWN
```

For example, an adapter may return `ACKNOWLEDGED` while authoritative verification remains inconclusive.

Likewise, an adapter may return `ERROR` even though authoritative verification later establishes that the external consequence became effective.

---

## Explicit Custody Orchestration

`execute_under_custody()` provides the explicit execution boundary.

Current flow:

```text
ExecutionAttempt
      |
      v
Decision
      |
      v
select_effect_for_custody()
      |
      v
validate_capability_for_custody()
      |
      v
EffectAdapter.execute(
    execution_attempt=...,
    effect=selected_effect,
    capability=...
)
      |
      v
AdapterExecutionResult
```

The orchestration enforces these protections:

- only `ADMITTED` and `NARROWED` can reach the adapter;
- `NARROWED` passes only `permitted_effect`;
- capability mismatch fails before adapter invocation;
- the adapter must return an `AdapterExecutionResult`;
- the returned result must preserve the expected execution lineage;
- no `Effect` is created during custody execution.

---

## EffectVerifier

External-state verification is intentionally separate from execution.

The vendor-neutral verification protocol is conceptually:

```python
class EffectVerifier(Protocol):
    def verify(
        self,
        *,
        adapter_result: AdapterExecutionResult,
    ) -> EffectVerificationResult:
        ...
```

Therefore:

```text
EffectAdapter
    -> attempts external mutation

EffectVerifier
    -> determines external reality
```

The generic core does not require the same component to implement both responsibilities.

---

## EffectVerificationResult

Current verification states are:

```text
VERIFIED_BOUND
VERIFIED_NO_BIND
INCONCLUSIVE
```

Conclusive verification states require verification references.

`INCONCLUSIVE` may have no references.

Effect conversion is explicit:

```text
VERIFIED_BOUND
    -> BOUND

VERIFIED_NO_BIND
    -> NO_BIND

INCONCLUSIVE
    -> EFFECT_UNKNOWN
```

Only an `EffectVerificationResult` can produce an Effect through:

```text
create_effect_from_verification()
```

There is deliberately no:

```text
AdapterExecutionResult -> Effect
```

shortcut.

---

## BOUND

`BOUND` means authoritative verification supports the claim that the intended permitted consequence became effective.

`BOUND` must not be inferred solely from:

- command submission;
- API acknowledgement;
- request acceptance;
- transport success;
- absence of errors.

The verification basis must support the Effect assertion.

---

## NO_BIND

`NO_BIND` means authoritative verification supports the claim that the intended consequence did not become effective.

`NO_BIND` must not be inferred merely because:

- execution was not attempted;
- execution returned an error;
- execution timed out;
- the connection failed;
- the response was lost;
- the adapter crashed;
- an acknowledgement was missing.

`VERIFIED_NO_BIND` requires verification references.

Failure is not proof of non-effect.

---

## EFFECT_UNKNOWN

When external reality cannot be established, CAGE uses:

```text
EFFECT_UNKNOWN
```

For example:

```text
execution request sent
        |
        v
adapter observation = ACKNOWLEDGED
        |
        v
authoritative verification = INCONCLUSIVE
        |
        v
EFFECT_UNKNOWN
```

CAGE preserves uncertainty rather than manufacturing `BOUND` or `NO_BIND`.

---

## Reconciliation

Reconciliation re-checks external reality for an existing external execution observation.

Current reconciliation flow is:

```text
existing AdapterExecutionResult
        |
        v
EffectVerifier
        |
        v
new EffectVerificationResult
```

`reconcile_effect_verification()` receives an existing `AdapterExecutionResult`.

It does not receive an `EffectAdapter`.

Therefore:

```text
reconciliation != replay
reconciliation != execution retry
reconciliation != re-execution
```

The same adapter result may be verified again later.

Example:

```text
one external execution
        |
        v
AdapterExecutionResult #1
        |
        v
Verification #1 = INCONCLUSIVE
        |
        v
Effect #1 = EFFECT_UNKNOWN
        |
        v
Warrant #1
        |
        v
reconcile same AdapterExecutionResult
        |
        v
Verification #2 = VERIFIED_BOUND
        |
        v
Effect #2 = BOUND
        |
        v
Warrant #2
```

The second Warrant may use:

```text
previous_warrant_id = first_warrant.warrant_id
```

while preserving the same Consequence, evaluation Attempt, ExecutionAttempt, and AdapterExecutionResult lineage.

Reconciliation changes CAGE's knowledge of external reality. It does not cause the external consequence to be executed again.

---

## Replay vs Execution Retry vs Reconciliation

These concepts remain distinct.

### Replay

Replay means:

```text
re-evaluate the Consequence
```

Replay creates a new evaluation `Attempt`.

Replay does not execute.

### Execution Retry

Execution retry means:

```text
attempt external execution again
```

A future retry operation would require a new `ExecutionAttempt` while preserving the same Consequence.

v0.6 defines the identity model needed for this distinction but does not introduce a broad retry orchestration feature.

### Reconciliation

Reconciliation means:

```text
verify external reality again
```

It uses an existing `AdapterExecutionResult`.

It does not automatically execute or re-evaluate the Consequence.

---

## Consequence-Level Execution Safety

The v0.5 consequence-level idempotency model remains foundational.

The same idempotency key plus the same business intent resolves to the same Consequence.

The same key with different business intent raises an idempotency conflict.

Custody preserves that Consequence identity through:

```text
Decision
ExecutionAttempt
AdapterExecutionResult
EffectVerificationResult
Effect
EffectProof
Warrant
```

Transport or provider retries must not silently become new business consequences.

---

## EffectProof

`EffectProof` is verification-backed.

It contains:

```text
proof_id
effect
verification
```

where `verification` must be an `EffectVerificationResult`.

`EffectProof` validates:

### Same Consequence

```text
Effect.consequence
==
EffectVerificationResult.consequence
```

### Matching verification and Effect state

```text
VERIFIED_BOUND    <-> BOUND
VERIFIED_NO_BIND  <-> NO_BIND
INCONCLUSIVE      <-> EFFECT_UNKNOWN
```

### Matching verification evidence

```text
Effect.verification_refs
==
EffectVerificationResult.references
```

It also derives:

```text
verification_id
adapter_result_id
execution_attempt_id
```

This prevents EffectProof from becoming an unsupported assertion detached from authoritative verification lineage.

---

## Warrant Evolution

A decision-only Warrant remains valid:

```text
Decision
    |
    v
DecisionProof
    |
    v
Warrant(effect_proof=None)
```

After authoritative effect verification:

```text
DecisionProof
    +
EffectProof
    |
    v
Warrant
```

When an `EffectProof` exists, Warrant derives:

```text
execution_attempt_id
adapter_result_id
verification_id
```

Reconciliation may create a later Warrant linked through:

```text
previous_warrant_id
```

Historical Warrants are not rewritten.

---

## Historical Integrity

Earlier uncertainty remains historically valid for the evidence available at that time.

For example:

```text
Warrant 1
Effect = EFFECT_UNKNOWN
```

may later be followed by:

```text
Warrant 2
Effect = BOUND
previous_warrant_id = Warrant 1
```

The second Warrant adds later authoritative knowledge. It does not erase the first Warrant's historical state.

---

## v0.6 Non-Negotiable Invariants

### Invariant 1 — Decision != Effect

A Decision is not evidence of external reality.

### Invariant 2 — ADMITTED does not automatically execute

Evaluation and external execution remain separate operations.

### Invariant 3 — Execution requires explicit custody

External mutation occurs only through an explicit custody execution path.

### Invariant 4 — Replay does not execute

Replay is evaluation-only.

### Invariant 5 — ExecutionAttempt != evaluation Attempt

They represent different events and maintain separate identity.

### Invariant 6 — Adapter execution result != Effect

Request-level adapter observations cannot establish `BOUND`, `NO_BIND`, or `EFFECT_UNKNOWN`.

### Invariant 7 — Uncertainty remains explicit

Unresolved external reality remains `EFFECT_UNKNOWN`.

### Invariant 8 — Consequence identity survives custody

Execution and verification lineage remain tied to the original Consequence.

### Invariant 9 — NARROWED executes only permitted_effect

The original broader requested effect must never reach the adapter.

### Invariant 10 — Execution capability is scoped

The capability must match the intended Consequence, action type, and resource.

### Invariant 11 — Effect claims require authoritative verification

Only verification-backed truth may produce an Effect.

### Invariant 12 — NO_BIND requires evidence of non-effect

Failure, timeout, rejection, or missing acknowledgement is insufficient.

### Invariant 13 — Reconciliation does not execute

Reconciliation verifies an existing adapter result and has no execution adapter parameter.

### Invariant 14 — Custody does not become IAM

CAGE models execution-authority scope without becoming a provider credential or policy system.

### Invariant 15 — Core remains vendor-neutral

No provider-specific cloud, database, payment, or identity semantics belong in generic Core.

### Invariant 16 — Historical assurance remains preserved

Later verification must not rewrite earlier uncertainty or earlier Warrants.

## Implemented v0.6 Core Model

```text
Consequence
    |
    +-- Evaluation Attempt A1
    |       |
    |       +-- Decision D1
    |       +-- DecisionProof
    |
    +-- ExecutionAttempt X1
            |
            +-- selected effect
            +-- scoped ExecutionCapability
            +-- EffectAdapter
            +-- AdapterExecutionResult R1
                    |
                    +-- Verification V1
                    |       |
                    |       +-- Effect E1
                    |       +-- EffectProof P1
                    |       +-- Warrant W1
                    |
                    +-- later reconciliation
                            |
                            +-- Verification V2
                            +-- Effect E2
                            +-- EffectProof P2
                            +-- Warrant W2
                                previous_warrant_id = W1
```

The Consequence remains the stable business identity throughout the lineage.

## v0.6 Design Test

Before adding any new Core abstraction, ask:

> Does this help CAGE safely carry an already-permitted consequence across the execution boundary and establish what actually became effective?

If the answer is no, it probably does not belong in v0.6 Consequence Custody.
