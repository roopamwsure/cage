# CAGE v0.6 — Consequence Custody

## Purpose

CAGE v0.6 introduces **Consequence Custody**.

Consequence Custody is the controlled boundary between a CAGE Decision and a real-world external system mutation.

v0.5 established whether an intended business consequence should be permitted and how that decision is preserved and proven.

v0.6 begins addressing the next problem:

> How can a permitted consequence be carried into external execution safely, with constrained authority, while preserving evidence of what actually became effective?

Consequence Custody must preserve the architectural separation established in v0.5:

```text
Decision != Effect
```

An ADMITTED Decision does not mean the consequence has been executed.

An execution attempt does not prove that the consequence became effective.

An execution failure does not prove NO_BIND.

External reality must be independently established before CAGE makes an Effect claim.

---

## Core Principle

A CAGE Decision authorizes a consequence for custody.

It does not itself execute the consequence.

The intended flow is:

```text
Action
  |
  v
Consequence
  |
  v
Attempt
  |
  v
Evaluation
  |
  v
Decision
  |
  v
DecisionProof
  |
  v
-----------------------------
     CONSEQUENCE CUSTODY
-----------------------------
  |
  v
Execution Attempt
  |
  v
Effect Adapter
  |
  v
External System
  |
  v
Authoritative Verification
  |
  v
Effect
  |
  v
EffectProof
  |
  v
Warrant
```

The custody boundary must prevent CAGE from confusing:

```text
permission to attempt execution
```

with:

```text
proof that execution became effective
```

---

## v0.6 Objectives

v0.6 should establish generic, vendor-neutral contracts for:

* controlled consequence execution;
* execution-attempt identity;
* Effect Adapter behavior;
* scoped execution capability;
* authoritative target-state verification;
* EFFECT_UNKNOWN handling;
* reconciliation;
* stronger NO_BIND guarantees;
* execution/replay separation.

v0.6 must remain usable without requiring AWS, Azure, GCP, or any other specific provider.

---

## Consequence Custody Boundary

The custody boundary begins only after CAGE has produced an appropriate Decision.

The custody subsystem must consume existing CAGE objects rather than recreate decision logic.

Conceptually:

```text
Consequence
    +
Decision
    +
DecisionProof
    |
    v
Custody
```

Custody must not reinterpret or modify the Decision.

For example:

```text
DecisionState.ADMITTED
```

may permit a custody operation to proceed.

But custody must not turn:

```text
ADMITTED
```

directly into:

```text
BOUND
```

An Effect can only be established through external verification.

---

## Execution Is Explicit

Execution must require an explicit custody operation.

The following must never happen:

```text
evaluate_attempt()
    |
    v
ADMITTED
    |
    v
automatic external execution
```

Instead:

```text
evaluate_attempt()
    |
    v
ADMITTED
    |
    v
DecisionProof
    |
    v
explicit custody request
    |
    v
execution attempt
```

This preserves developer control and prevents evaluation, replay, or proof construction from accidentally mutating external systems.

---

## Execution Attempt Identity

v0.6 requires a new concept distinct from the v0.5 evaluation Attempt.

An evaluation Attempt represents:

> one evaluation of a Consequence.

An execution attempt represents:

> one attempt to make that Consequence effective in an external system.

These must not be conflated.

Conceptually:

```text
Consequence C1

Evaluation Attempt A1
    |
    v
Decision D1
    |
    v
Execution Attempt X1
```

A later execution retry might create:

```text
Execution Attempt X2
```

while still referring to:

```text
same Consequence C1
```

Execution-attempt identity must survive independently from:

* evaluation Attempt identity;
* API request identity;
* agent session identity;
* retry number;
* transport retry.

---

## Effect Adapter

An Effect Adapter is the vendor-neutral execution boundary between CAGE custody and an external system.

The generic Effect Adapter contract should eventually support two distinct responsibilities:

```text
execute intended consequence
```

and:

```text
verify resulting external state
```

These responsibilities must remain logically distinct even if one adapter implements both.

An Effect Adapter must not decide whether the consequence is allowed.

That decision already belongs to CAGE evaluation.

An Effect Adapter must not implement:

* IAM policy evaluation;
* business authorization logic;
* approval workflow logic;
* CAGE Decision logic.

Its responsibility is execution and external-state verification.

---

## Adapter Neutrality

Generic CAGE Core must not contain adapters specifically for:

* AWS;
* Azure;
* GCP;
* Kubernetes;
* databases;
* payment systems;
* identity platforms;
* ServiceNow;
* SaaS applications.

Provider-specific adapters may be implemented later outside generic Core.

The generic v0.6 contracts should be sufficient for future adapters to integrate without changing core consequence semantics.

---

## Scoped Capability

External execution must not require giving an adapter unrestricted authority.

v0.6 should introduce a generic concept of a **scoped execution capability**.

The capability should represent authority sufficient to attempt only the intended consequence or a tightly bounded set of permitted operations.

Conceptually:

```text
Consequence
    |
    v
Scoped Capability
    |
    v
Effect Adapter
```

The capability must not imply that CAGE itself becomes an IAM system.

CAGE may consume or transport a constrained capability produced by an external credential or authorization system.

CAGE should not recreate provider IAM semantics.

---

## Capability Requirements

A scoped execution capability should eventually be constrained by factors such as:

* intended resource;
* intended operation;
* permitted effect;
* validity period;
* consequence identity;
* execution context.

The exact provider-specific enforcement mechanism belongs outside generic Core.

The generic Core should model the assurance boundary without embedding AWS IAM, Azure RBAC, OAuth scopes, cloud tokens, or similar implementation details.

---

## Permitted Effect and Execution

For a normal ADMITTED Decision, the requested effect remains the intended permitted effect.

For a NARROWED Decision, custody must execute only the explicit `permitted_effect`.

It must never execute the original broader requested effect.

Conceptually:

```text
Requested Effect
Global Admin / 480 minutes

Decision
NARROWED

Permitted Effect
Scoped Operator / 30 minutes
```

Custody must operate against:

```text
Scoped Operator / 30 minutes
```

not the original request.

This is a critical execution invariant.

---

## Execution Result Is Not Effect

An Effect Adapter may receive an API response such as:

```text
HTTP 200
success=true
request accepted
operation queued
```

None of these responses alone necessarily prove that the business consequence became effective.

Therefore:

```text
Execution Result != Effect
```

A successful API call may still result in:

```text
EFFECT_UNKNOWN
```

until authoritative verification establishes the external state.

Similarly:

```text
Execution Error != NO_BIND
```

because the external system may have applied the change before the error or timeout occurred.

---

## Authoritative Verification

CAGE may assert an Effect only when the available verification basis is strong enough for the claim.

The verification mechanism should establish the relevant target state independently of the execution request response when necessary.

Examples may eventually include:

* authoritative resource state;
* system-of-record state;
* target object existence or absence;
* authoritative transaction status;
* authoritative identity or permission state.

Provider-specific verification remains outside generic Core.

Generic Core should only model:

* verification evidence;
* resulting Effect state;
* verification references.

---

## BOUND

BOUND means there is adequate verification that the intended permitted consequence became effective.

BOUND must not be inferred solely from:

* command submission;
* API acknowledgement;
* request acceptance;
* transport success;
* absence of errors.

The strength of verification must support the assertion being made.

---

## NO_BIND

NO_BIND means there is adequate verification that the intended consequence did not become effective.

NO_BIND must not be inferred merely because:

* execution was not attempted;
* execution returned an error;
* execution timed out;
* the connection failed;
* the response was lost;
* the adapter crashed;
* an execution acknowledgement was missing.

NO_BIND requires evidence of non-effect.

This remains one of the strongest CAGE invariants.

---

## EFFECT_UNKNOWN

When external reality cannot be established, CAGE must use:

```text
EFFECT_UNKNOWN
```

For example:

```text
execution request sent
        |
        v
network timeout
        |
        v
external state cannot yet be verified
        |
        v
EFFECT_UNKNOWN
```

CAGE must preserve uncertainty rather than converting it into BOUND or NO_BIND.

---

## Reconciliation

v0.6 should support reconciliation of unresolved external consequences.

Reconciliation means:

> re-checking external reality for an existing Consequence without creating a new business consequence.

For example:

```text
Execution Attempt X1
        |
        v
EFFECT_UNKNOWN
        |
        v
later verification
        |
        +-- BOUND
        |
        +-- NO_BIND
        |
        +-- remains EFFECT_UNKNOWN
```

Reconciliation must preserve the original Consequence identity.

It must not automatically execute the consequence again.

---

## Replay vs Execution Retry vs Reconciliation

These concepts must remain distinct.

### Replay

Replay means:

```text
re-evaluate the Consequence
```

It creates a new evaluation Attempt.

Replay does not execute the consequence.

### Execution Retry

Execution retry means:

```text
attempt external execution again
```

It creates a new execution-attempt identity.

Execution retry must be subject to consequence-level safety and idempotency rules.

### Reconciliation

Reconciliation means:

```text
verify external reality again
```

It does not automatically execute or re-evaluate the consequence.

The three operations must never be treated as interchangeable.

---

## Consequence-Level Execution Safety

Execution retries must preserve the existing Consequence identity.

A transport retry, agent retry, adapter retry, or API retry must not silently create a new business consequence.

The existing v0.5 consequence-level idempotency semantics remain foundational.

v0.6 must extend those semantics into execution custody without weakening them.

---

## Decision Eligibility for Custody

Custody must not execute every Decision state.

At minimum:

```text
ADMITTED
```

may be eligible for custody.

```text
NARROWED
```

may be eligible for custody using only its `permitted_effect`.

The behavior of:

```text
HELD
ESCALATED
REFUSED
```

must not permit execution of the requested consequence.

The exact generic eligibility contract should be defined before implementation.

---

## Failure Must Be Explicit

Custody must never silently reinterpret abnormal conditions.

Examples:

```text
missing capability
invalid adapter result
verification failure
adapter exception
timeout
unsupported operation
```

must not silently become:

```text
BOUND
```

or:

```text
NO_BIND
```

where evidence does not support those claims.

Failure and uncertainty must remain explicit.

---

## Warrant Evolution

v0.6 extends the existing Warrant lifecycle.

A v0.5-style Warrant may initially contain:

```text
DecisionProof
EffectProof = absent
```

After custody and verification, a later Warrant may contain:

```text
DecisionProof
EffectProof
```

For unresolved execution:

```text
DecisionProof
EffectProof(EFFECT_UNKNOWN)
```

A later reconciliation may produce a subsequent Warrant containing:

```text
EffectProof(BOUND)
```

or:

```text
EffectProof(NO_BIND)
```

Warrant lineage should preserve this evolution without rewriting historical assurance claims.

---

## Historical Integrity

Existing Decisions, Effect assertions, Attempts, execution attempts, and Warrants should remain historical records.

Later verification must not mutate the meaning of earlier evidence.

For example:

```text
Warrant 1
Effect = EFFECT_UNKNOWN
```

may later be followed by:

```text
Warrant 2
Effect = BOUND
previous_warrant_id = Warrant 1
```

The earlier uncertainty remains historically true for the evidence available at that time.

---

## v0.6 Non-Negotiable Invariants

### Invariant 1 — ADMITTED does not automatically execute

Evaluation and external execution remain separate operations.

### Invariant 2 — Execution requires explicit custody

External mutation must occur only through an explicit custody operation.

### Invariant 3 — Replay does not execute

Replay remains evaluation-only.

### Invariant 4 — Execution result does not determine Effect

API success does not automatically imply BOUND.

API failure does not automatically imply NO_BIND.

### Invariant 5 — Uncertainty remains explicit

Unverified external state must remain EFFECT_UNKNOWN.

### Invariant 6 — Execution preserves Consequence identity

Retries and execution attempts must continue to refer to the same intended business consequence.

### Invariant 7 — Execution attempts have distinct identity

Each external execution attempt must be separately identifiable.

### Invariant 8 — NARROWED execution uses only the permitted effect

Custody must not execute the original broader requested effect.

### Invariant 9 — Capability is scoped

Execution authority should be constrained to the intended consequence rather than represented as unrestricted ambient authority.

### Invariant 10 — Effect claims require verification

Effect assertions must not exceed the available verification evidence.

### Invariant 11 — NO_BIND requires evidence of non-effect

Failure, timeout, or absence of acknowledgement is insufficient.

### Invariant 12 — Reconciliation does not re-execute

Reconciliation establishes external state and must not implicitly perform the consequence again.

### Invariant 13 — Custody does not become IAM

CAGE may consume constrained capabilities but must not recreate provider IAM systems.

### Invariant 14 — Core remains vendor-neutral

No cloud, database, payment, or identity provider semantics belong in generic custody contracts.

### Invariant 15 — Historical assurance remains preserved

Later verification must not rewrite earlier uncertainty or earlier assurance artifacts.

---

## Initial v0.6 Conceptual Model

The intended model is approximately:

```text
Consequence
    |
    +-- Evaluation Attempt A1
    |       |
    |       +-- Decision
    |       +-- DecisionProof
    |
    +-- Execution Attempt X1
    |       |
    |       +-- Adapter execution
    |       +-- verification
    |       +-- Effect
    |
    +-- Execution Attempt X2
            |
            +-- retry if explicitly authorized
            +-- verification
            +-- Effect
```

All of these remain associated with the same Consequence.

## Proposed v0.6 Development Sequence

Implementation should proceed in small independent slices.

### Step 1 — Consequence Custody semantics

Define the architecture, invariants, and scope.

### Step 2 — Execution Attempt identity

Introduce a generic execution-attempt model without performing execution.

### Step 3 — Effect Adapter contract

Define the minimal vendor-neutral adapter interface.

### Step 4 — Custody eligibility

Define which Decisions may enter custody and which effect is eligible for execution.

### Step 5 — Scoped capability model

Introduce the smallest generic capability contract needed for execution custody.

### Step 6 — Explicit execution orchestration

Allow an explicit custody operation to invoke an adapter.

### Step 7 — Verification contract

Separate execution response from authoritative external-state verification.

### Step 8 — Effect establishment

Produce BOUND, NO_BIND, or EFFECT_UNKNOWN only from appropriate verification outcomes.

### Step 9 — Reconciliation

Allow unresolved consequences to be verified again without re-execution.

### Step 10 — Retry and idempotency safety

Prove repeated execution attempts cannot silently create duplicate business consequences.

### Step 11 — Warrant lifecycle

Connect custody verification to EffectProof and subsequent Warrant lineage.

### Step 12 — Cross-domain scenarios

Prove the same custody architecture works across materially different domains.

### Step 13 — v0.6 Definition of Done review

Do not proceed to v0.7 until the custody invariants are demonstrably satisfied.

## v0.6 Design Test

Before adding any new Core abstraction, ask:

> Does this help CAGE safely carry an already-permitted consequence across the execution boundary and establish what actually became effective?

If the answer is no, it probably does not belong in v0.6 Consequence Custody.
