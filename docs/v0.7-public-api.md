# CAGE v0.7 — Public API

Status: implemented developer SDK contract.

Date: 2026-09-19

Original design baseline: `roopamwsure/cage`, commit
`476c4930a909a593cfa8f55e92b390d3811578f7` (`v0.6.0`). The original source
review ran 279 tests on Python 3.12.14 with pytest 8.4.2. That result is retained
as a historical v0.6 baseline, not as evidence for later v0.7 behavior.

The v0.7 SDK now implements `CAGE.evaluate()`, `execute()`, `verify()`, and
`reconcile()`, typed result wrappers, facade-local lifecycle guards, identifier
overrides, input helpers, portable Warrant support, and the documented import
surfaces. The installed CLI includes Warrant inspection and validation together
with the three disposable local examples.

For usage, see the [Quickstart](quickstart.md),
[Integration guide](integration-guide.md),
[Failure and recovery](failure-and-recovery.md), and
[Portable Warrants and CLI](portable-warrants-and-cli.md).

## 1. Purpose and scope

The facade gives developers four lifecycle methods:

```text
evaluate
execute
verify
reconcile
```

They provide a higher-level orchestration layer over the existing Core without
creating a second Decision or Effect engine.

The public API preserves the same fundamental separations as Core:

```text
Decision != Effect
Evaluation Attempt != ExecutionAttempt
AdapterExecutionResult != Effect
Execution != Verification
Reconciliation != Re-execution
```

Sections 2–8 define construction, method contracts, results, identity, and
source mapping. Sections 9–14 define dispatch guards and failure recovery.
Sections 15–22 define configuration, imports, helpers, portable Warrants, CLI
behavior, and acceptance checks. Section 23 records implementation history.

---

## 2. Construction and ownership

```text
CAGE(
    *,
    rule: EvaluationRule,
    config: CAGEConfig | None = None,
)
```

`rule` is required. It receives the evaluation Attempt together with tuples of
Evidence, Standing, Delegation, Approval, and Context and returns an
`EvaluationOutcome`.

There is no default rule that silently admits an action. The application owns
the domain-specific question of which assurance facts are sufficient.

Each facade instance owns an in-memory `IdempotencyRegistry` and the local
lifecycle guards described later in this document. A different facade or a
restarted process does not inherit that state.

`config=None` selects the defaults in section 15. Configuration cannot disable
custody, capability validation, verification, or the local dispatch guard.

## 3. Method contracts

### 3.1 `evaluate()`

```text
evaluate(
    *,
    action: Action,
    idempotency_key: str,
    evidence: Sequence[Evidence] = (),
    standing: Sequence[Standing] = (),
    delegations: Sequence[Delegation] = (),
    approvals: Sequence[Approval] = (),
    context: Sequence[Context] = (),
    previous: EvaluationResult | None = None,
    ids: EvaluationIds | None = None,
) -> EvaluationResult
```

The caller supplies an existing `Action` and a stable business-operation
`idempotency_key`.

The facade:

1. validates SDK arguments and fixes the assurance-input snapshot;
2. constructs a candidate Consequence and resolves it through
   `IdempotencyRegistry.resolve()`;
3. creates an evaluation Attempt for the resolved Consequence;
4. calls `evaluate_attempt()` with the configured rule;
5. creates `DecisionProof` from the same assurance-input snapshot; and
6. returns an `EvaluationResult` containing a decision-only Warrant.

All Decision states are normal outcomes. `REFUSED`, `HELD`, or `ESCALATED` do
not become exceptions simply because execution is unavailable.

`evaluate()` never invokes an adapter or verifier and never creates an Effect.

When `previous` is supplied, the call is an explicit replay. The Action and key
must resolve consistently with the earlier Consequence. A new evaluation
Attempt is created and the new decision-only Warrant points to the predecessor
Warrant. Replay does not silently become a new business Consequence.

Repeated equivalent evaluations without `previous` may resolve to the same
Consequence while creating distinct evaluation Attempts.

### 3.2 `execute()`

```text
execute(
    evaluation: EvaluationResult,
    *,
    adapter: EffectAdapter,
    capability: ExecutionCapability,
    execution_attempt_id: str | None = None,
) -> ExecutionResult
```

The method takes the complete `EvaluationResult`, preserving its DecisionProof
and Warrant lineage.

The facade creates an `ExecutionAttempt` for the exact Decision and delegates
to `execute_under_custody()`.

Core custody remains authoritative for:

- Decision eligibility;
- exact effect selection;
- capability-scope validation;
- adapter invocation; and
- returned execution-lineage validation.

The state mapping is:

```text
ADMITTED
    -> original RequestedEffect

NARROWED
    -> Decision.permitted_effect

HELD
ESCALATED
REFUSED
    -> custody ineligible
```

The caller supplies `ExecutionCapability`. An admitted Decision does not create
authority automatically.

Adapter states `ACKNOWLEDGED`, `REJECTED`, `ERROR`, and `UNKNOWN` are execution
observations. None of them creates an Effect or EffectProof.

`execute()` does not call a verifier and does not automatically retry. Within
one facade instance, once dispatch may have begun for the canonical
Consequence, a later `execute()` for that same Consequence is rejected by the
local dispatch guard described in sections 9–11.

### 3.3 `verify()`

```text
verify(
    execution: ExecutionResult,
    *,
    verifier: EffectVerifier,
    ids: AssuranceIds | None = None,
) -> AssuranceResult
```

`verify()` observes the exact `AdapterExecutionResult` retained in
`execution`.

The facade uses the existing verification helpers to invoke the verifier,
validate returned lineage, create the Effect, create EffectProof, and construct
a Warrant that preserves the original DecisionProof.

The verification-to-Effect mapping is:

| Verification | Effect |
| --- | --- |
| `VERIFIED_BOUND` | `BOUND` |
| `VERIFIED_NO_BIND` | `NO_BIND` |
| `INCONCLUSIVE` | `EFFECT_UNKNOWN` |

Both conclusive verification states require references. `INCONCLUSIVE` is a
normal result, not an exception.

Verification never executes the operation.

Within one `CAGE` instance, only one completed first verification is reserved
per execution. A concurrent or repeated `verify()` raises
`DuplicateVerificationError`. The exception exposes the original execution and,
when available, the completed `AssuranceResult`. A failed verification releases
the reservation so the caller can retry observation with the same execution.

After a successful first verification, later observations use `reconcile()`.

### 3.4 `reconcile()`

```text
reconcile(
    previous: AssuranceResult,
    *,
    verifier: EffectVerifier,
    ids: AssuranceIds | None = None,
) -> AssuranceResult
```

`previous` carries the prior Warrant and the original execution context.

The facade reuses the existing `AdapterExecutionResult`, performs another
verification, and creates a new Effect, EffectProof, and Warrant.

The new Warrant sets:

```text
previous_warrant_id = previous.warrant.warrant_id
```

The Consequence, evaluation lineage, ExecutionAttempt, AdapterExecutionResult,
and DecisionProof remain part of the same path. Earlier records are not
modified.

`reconcile()` accepts no adapter or capability and creates no new
ExecutionAttempt.

A later observation can remain `INCONCLUSIVE`; reconciliation is not guaranteed
to make the state more certain.

Within one facade instance, a predecessor assurance has one reserved completed
successor. A duplicate call raises `DuplicateReconciliationError`. Failed
reconciliation releases that reservation so observation can be retried from the
same predecessor.

## 4. Typed result contracts

The result wrappers are immutable views over existing domain records.

| Result | Authoritative contents | Read-only convenience access |
| --- | --- | --- |
| `EvaluationResult` | Decision-only `warrant: Warrant` | `decision`, `decision_proof`, `attempt`, `consequence`, `consequence_id`, `idempotency_key` |
| `ExecutionResult` | `evaluation`, `capability`, `adapter_result`, `observation_origin` | `decision`, `decision_proof`, `execution_attempt`, `consequence_id`, `idempotency_key` |
| `AssuranceResult` | `execution`, assurance `warrant` | `decision`, `decision_proof`, `execution_attempt`, `adapter_result`, `observation_origin`, `verification`, `effect`, `effect_proof`, `consequence_id`, `idempotency_key` |

`EvaluationResult` requires a Warrant without EffectProof.

`AssuranceResult` requires a Warrant with EffectProof.

The wrappers validate full lifecycle consistency rather than accepting a shared
Consequence ID as sufficient proof that unrelated records belong together.

Before verification there is no authoritative Effect. That differs from an
`AssuranceResult` whose verified Effect is `EFFECT_UNKNOWN`.

There is no generic `success` property. Applications inspect the specific
Decision, adapter, verification, and Effect states they need.

`ExecutionObservationOrigin` has two runtime values:

```text
ADAPTER       = "adapter"
SDK_RECOVERY  = "sdk_recovery"
```

It records who produced the execution observation, not who established the
external Effect. That provenance remains visible through verification,
reconciliation, inspection, and portable export.

## 5. Identity defaults and explicit overrides

Two optional override objects keep common calls small:

| Override object | Optional fields (`str | None`) |
| --- | --- |
| `EvaluationIds` | `consequence_id`, `attempt_id`, `decision_id`, `decision_proof_id`, `warrant_id` |
| `AssuranceIds` | `effect_id`, `effect_proof_id`, `warrant_id` |

Omitted fields receive generated IDs. `execution_attempt_id` remains a direct
optional parameter.

ID ownership follows the existing contracts:

- the facade owns IDs for records it creates;
- existing Action and assurance-input records keep their supplied identities;
- an adapter owns the ID of a valid returned `AdapterExecutionResult`;
- the facade owns the ID of an SDK recovery observation;
- a verifier owns `EffectVerificationResult.verification_id`; and
- the facade never silently replaces IDs returned by integrations.

An explicit `consequence_id` proposes the identity for a new Consequence. If an
idempotency key already resolves to an equivalent canonical Consequence, that
existing identity remains authoritative.

Replay and reconciliation must not reuse predecessor event identities.

## 6. Why `idempotency_key` is required

The application chooses the key for one intended business operation and reuses
it when reevaluating or recovering that same operation.

A different intended operation needs a different key even when some parameters
are identical.

Generating a random key on every call would defeat repeated-request detection.
Deriving the key only from effect parameters could conflate distinct business
operations.

CAGE therefore does not silently invent this business identity.

Matching the same key and equivalent intent preserves Consequence identity
within the registry's scope. It does not provide external exactly-once
execution or cross-process coordination.

---

## 7. Evidence and error boundaries

Failures after possible dispatch keep the original execution identity and the
context needed for later observation.

They do not imply `NO_BIND`, create a replacement Consequence, or trigger an
automatic execution retry.

When no usable adapter result exists after possible dispatch, the SDK creates a
clearly labelled local recovery observation. Only a verifier can later establish
an Effect.

The SDK does not invent a successful adapter acknowledgement or successful
verification.

## 8. Source mapping

| Responsibility | Existing Core contract |
| --- | --- |
| Resolve equivalent business intent | `IdempotencyRegistry.resolve()` in `idempotency.py` |
| Create replay lineage | `create_replay_attempt()` in `replay.py` |
| Evaluate assurance inputs | `evaluate_attempt()` in `evaluation.py` |
| Capture Decision provenance | `create_decision_proof()` in `warrant.py` |
| Enforce custody and execute | `execute_under_custody()` in `custody.py` |
| Invoke verifier and check lineage | `reconcile_effect_verification()` in `verification.py` |
| Establish Effect | `create_effect_from_verification()` in `verification.py` |
| Bind Effect to verification | `create_effect_proof()` in `warrant.py` |
| Preserve snapshots and predecessors | `Warrant` in `warrant.py` |

The facade adds orchestration around these contracts. It does not copy their
Decision or Effect semantics into another engine.

## 9. One dispatch per Consequence within a facade instance

Once adapter dispatch may have begun for a Consequence, that `CAGE` instance
will not dispatch it again.

A repeated `execute()` raises `DuplicateExecutionError`. It does not call the
adapter again, return a fabricated cached success, or create a second
ExecutionAttempt representing another external invocation.

The guard uses the canonical Consequence from the idempotency registry. A new
evaluation Attempt or Decision does not reset it.

The record remains consumed after:

- any valid adapter result, including `REJECTED`, `ERROR`, or `UNKNOWN`;
- an adapter exception, invalid return, or mismatched result after possible
  dispatch;
- verification resulting in any Effect state; or
- a verifier or local assurance-assembly failure after dispatch.

Even verified `NO_BIND` does not automatically authorize another execution.
General execution-retry orchestration is outside v0.7.

The guard is local to one live facade. It does not coordinate another process,
another `CAGE` instance, or direct low-level Core calls.

## 10. Dispatch tracking and concurrency

The facade keeps small in-memory lifecycle records for guarded Consequences.

The execution sequence is:

1. validate SDK inputs and lifecycle consistency;
2. allocate required ExecutionAttempt and recovery IDs before dispatch;
3. atomically reserve the canonical Consequence;
4. delegate to `execute_under_custody()` through a thin wrapper that marks
   adapter entry;
5. release the reservation only if failure is known to have occurred before the
   adapter could be invoked; and
6. retain the reservation once adapter entry may have occurred.

The wrapper does not hide invalid adapter behavior. Custody remains responsible
for eligibility, effect selection, capability checks, and returned-lineage
validation.

The state lock protects registry and reservation updates, but user rules,
adapters, and verifiers are not run while holding it.

An exception class name by itself cannot prove that no external mutation was
possible after adapter entry.

## 11. Adapter failure and recoverable execution context

### 11.1 Valid adapter results

A valid adapter result with matching lineage returns an `ExecutionResult` with
origin `ADAPTER`, regardless of adapter state.

An explicit adapter `ERROR` is therefore a typed outcome. A Python exception
escaping the adapter is an invocation failure.

### 11.2 No usable adapter result

For an adapter exception, invalid return type, or mismatched execution result,
the facade raises a typed execution error whose `execution` attribute preserves
recoverable context.

That execution contains an SDK-generated `AdapterExecutionResult` with:

```text
new SDK result_id
original ExecutionAttempt
state = UNKNOWN
reference = urn:cage:sdk:recovery-observation
observation_origin = SDK_RECOVERY
```

This means no usable adapter outcome is available. It does not assert that the
adapter returned `UNKNOWN`, that the target accepted anything, or that an Effect
exists.

If a valid adapter result had already been obtained before a later local
assembly failure, the SDK retains that original observation and `ADAPTER`
origin instead of replacing it.

A mismatched result is never repaired by rewriting its execution ID or copying
its receipts onto the expected attempt.

### 11.3 Recovery through verification

The recovery path is:

```python
verify(error.execution, verifier=...)
```

It reuses the original execution context and does not dispatch again.

If target evidence is insufficient, the verifier returns `INCONCLUSIVE`, which
produces `EFFECT_UNKNOWN` through the normal Core mapping.

Later `reconcile()` calls continue to observe that same recovery record. The
record remains labelled `SDK_RECOVERY` even if later evidence establishes
`BOUND` or `NO_BIND`.

---

## 12. Verification failures and repeated observation

A verifier returning `INCONCLUSIVE` is a normal result.

A verifier raising, returning the wrong type, or returning a result for another
adapter result is an error.

Such errors retain the original execution and, during reconciliation, the prior
assurance. No replacement verification, Effect, EffectProof, or Warrant is
invented.

Recovery from an initial verification error is another explicit `verify()`.
Recovery from a reconciliation error is another explicit `reconcile()` using
the retained predecessor.

If verification succeeded but later Effect/proof/Warrant assembly failed, the
valid verification remains available in the error context.

Previously returned assurance records remain historical snapshots.

## 13. Exception contracts

Public SDK exceptions share a `CAGEError` base where appropriate. Normal
Decision, adapter, and verification states do not become exceptions merely
because they are unfavorable.

Current implemented names include:

```text
AdapterInvocationError
AdapterContractError
AdapterResultMismatchError
DuplicateExecutionError
DuplicateVerificationError
DuplicateReconciliationError
VerifierInvocationError
VerifierContractError
VerificationResultMismatchError
AssuranceAssemblyError
IdentifierGenerationError
IdentityConflictError
WarrantExportError
WarrantFormatError
UnsupportedWarrantVersionError
WarrantIOError
```

`AdapterInvocationError`, `AdapterContractError`, and
`AdapterResultMismatchError` retain recoverable execution context after possible
dispatch.

Verifier and assurance errors retain `execution`; reconciliation failures also
retain `previous`. `AssuranceAssemblyError` additionally retains the valid
`verification` and failed assembly `stage`.

Earlier design notes used names such as `EvaluationRuleError`,
`EvaluationContractError`, `ExecutionFinalizationError`,
`VerificationInvocationError`, `VerificationContractError`, and
`AssuranceFinalizationError`. Those names are historical design targets and are
not exported by the current SDK.

Existing Core exceptions keep their direct-call behavior. Where the SDK wraps a
Core domain failure, compatibility with the corresponding Core exception family
is preserved where documented.

Error messages should distinguish local validation, adapter contract failure,
unknown external outcome, and failed observation without automatically exposing
provider payloads or credentials.

## 14. Behavioral checks

The implementation is expected to preserve these behaviors:

| Scenario | Required outcome |
| --- | --- |
| Refused Decision or mismatched capability | Adapter called zero times; no claimed Effect |
| Corrected request after confirmed pre-dispatch failure | A later explicit call may reach custody |
| Same Consequence executed twice | At most one adapter dispatch through this facade; duplicate call raises `DuplicateExecutionError` |
| Replay after dispatch | New evaluation does not bypass the dispatch guard |
| Two threads evaluate the same key and execute | One canonical Consequence and at most one dispatch through this facade |
| Adapter mutates then raises | Recovery context retained; verification may establish `BOUND`; no second dispatch |
| Adapter raises before observable mutation | No inferred `NO_BIND` |
| Adapter returns malformed or mismatched data | Contract error plus labelled recovery observation |
| Adapter returns valid `REJECTED` or `ERROR` | Normal ExecutionResult; no automatic Effect or redispatch |
| Recovery observation lacks enough evidence | `INCONCLUSIVE` -> `EFFECT_UNKNOWN` |
| Verifier fails | No new Effect or Warrant; retained context remains usable |
| Reconciliation resolves uncertainty | New Warrant links to predecessor; adapter count unchanged |
| Different facade or process | No claim of shared dispatch protection or restart restoration |

## 15. Minimal configuration and identity generation

`CAGEConfig` is immutable and currently exposes one configurable field:

| Field | Type | Default |
| --- | --- | --- |
| `id_factory` | `IdFactory` | `uuid_id` |

`IdFactory` is:

```text
(kind: IdentityKind) -> str
```

`uuid_id` uses the Python standard library and returns opaque identifiers of the
form `<kind.value>_<uuid4 hex>`.

`IdentityKind` includes:

| Member | Value | Typical owner |
| --- | --- | --- |
| `ACTION` | `action` | Input helper |
| `CONSEQUENCE` | `consequence` | Facade |
| `ATTEMPT` | `attempt` | Facade |
| `DECISION` | `decision` | Facade |
| `DECISION_PROOF` | `decision_proof` | Facade |
| `EXECUTION_ATTEMPT` | `execution_attempt` | Facade |
| `ADAPTER_RESULT` | `adapter_result` | Adapter or SDK recovery observation |
| `VERIFICATION` | `verification` | Verifier |
| `EFFECT` | `effect` | Facade |
| `EFFECT_PROOF` | `effect_proof` | Facade |
| `WARRANT` | `warrant` | Facade |
| `EVIDENCE` | `evidence` | Input helper |
| `STANDING` | `standing` | Input helper |
| `DELEGATION` | `delegation` | Input helper |
| `APPROVAL` | `approval` | Input helper |
| `CONTEXT` | `context` | Input helper |

Factories must return nonblank strings. Invalid factory configuration raises the
appropriate SDK type/value error; a factory that raises produces
`IdentifierGenerationError` retaining the requested kind and cause.

Known local identity conflicts raise `IdentityConflictError` before dispatch
where possible. Invalid overrides remain `CAGEValueError`; conflicting business
keys remain `IdempotencyConflictError`.

Custom factories used concurrently must be thread-safe.

The facade exposes read-only `config` and `inputs` properties. Input helpers use
the configured factory and the same local identity checks.

Facade-created Warrants use `schema_version="0.7"`. This Core-record label is
separate from the portable Warrant format version and from package patch
versions.

v0.7 does not add environment loaders, global registries, clock services,
network settings, execution-retry switches, or safety-disable flags to
`CAGEConfig`.

`cage.inputs` creates the existing immutable Core objects, generating record IDs
where omitted and delegating validation/freezing to the Core constructors.

The supported helper shapes are:

```text
cage.inputs.action(
    *, action_type: str, principal_id: str, agent_id: str,
    resource_id: str, requested_effect: Mapping[str, object],
    action_id: str | None = None,

cage.inputs.evidence(
    *, evidence_type: str, subject: str, source: str,
    data: Mapping[str, object], evidence_id: str | None = None,
) -> Evidence

cage.inputs.standing(
    *, standing_type: str, subject: str, source: str,
    attributes: Mapping[str, object], standing_id: str | None = None,

cage.inputs.delegation(
    *, delegator: str, delegatee: str, source: str,
    scope: Mapping[str, object], delegation_id: str | None = None,
) -> Delegation

cage.inputs.approval(
    *, approval_type: str, approver: str, subject: str, source: str,
    scope: Mapping[str, object], approval_id: str | None = None,

    *, context_type: str, source: str,
```

The installed examples are teaching fixtures:

The original design required release installation guidance not to claim PyPI
availability before publication had been verified. That condition was later
satisfied: the current published package is `cage-assurance==0.7.1`.

## 18. Portable Warrant API

Portable records are detached inspection data. Parsing them does not recreate a
live EvaluationResult, ExecutionResult, capability, dispatch guard, or authority
to execute.

`WarrantDisclosure` is:

```text
SUMMARY = "summary"
FULL    = "full"
```

`SUMMARY` is the default.

```text
export_warrant(
    source: Warrant | EvaluationResult | AssuranceResult,
    *, disclosure: WarrantDisclosure = WarrantDisclosure.SUMMARY,
) -> PortableWarrant

parse_warrant(data: str | bytes) -> PortableWarrant

load_warrant(path: str | Path) -> PortableWarrant

dump_warrant(
    document: PortableWarrant,
    path: str | Path,
    *, overwrite: bool = False,
) -> None

validate_warrant(
    data: str | bytes | PortableWarrant,
) -> WarrantValidationReport
```

`PortableWarrant` is immutable and exposes typed read-only properties including
format/disclosure metadata, lifecycle IDs and states, predecessor identity, and
observation origin. Execution/Effect properties are `None` when those records
are absent.

It also provides `to_dict()` and `to_json()`. JSON formatting is for storage or
display and is not cryptographic canonicalization.

`export_warrant()` validates lifecycle consistency before projection. Facade
results provide explicit observation origin. For a bare legacy Core Warrant,
origin is `unspecified` unless the reserved SDK recovery marker establishes
recovery provenance.

A portable record represents one internally consistent Decision/execution path.
An inconsistent raw Warrant is rejected rather than flattened into a portable
claim.

`ExecutionResult` is not an export source. Its evaluation Warrant can be
exported as a decision-only record.

`load_warrant()` and `dump_warrant()` use UTF-8. Dump refuses an existing path
unless `overwrite=True` and validates/serializes before replacement.

Additional public exceptions include `WarrantExportError`, `WarrantFormatError`,
`UnsupportedWarrantVersionError`, and `WarrantIOError` together with the SDK
identity errors described above.

`validate_warrant()` returns a report rather than raising for malformed record
content. Invalid API argument types still raise `CAGETypeError`.

## 19. Portable Warrant format v1

The envelope requires:

```text
format = "cage.warrant"
format_version = "1"
```

The native Warrant `schema_version` is separate metadata.

Every top-level field is required. Format v1 has no unspecified extension
fields.

| Top-level field | Contents |
| --- | --- |
| `format` | literal `"cage.warrant"` |
| `format_version` | literal `"1"` |
| `disclosure` | profile and exact omitted-field paths |
| `warrant` | `warrant_id`, `schema_version`, nullable predecessor ID |
| `consequence` | `consequence_id`, `action_id`, nullable idempotency key in SUMMARY |
| `action` | action identity/type, Principal/Agent/Resource IDs, RequestedEffect |
| `evaluation_attempt` | Attempt identity, Consequence identity, nullable predecessor Attempt |
| `decision` | Decision identity, Attempt identity, state, nullable `permitted_effect` |
| `decision_proof` | proof identity, Decision identity, assurance reference arrays/counts |
| `execution_attempt` | object or `null` |
| `adapter_result` | object or `null` |
| `verification` | object or `null` |
| `effect` | object or `null` |
| `effect_proof` | object or `null` |

`EffectData` is exactly an object with `parameters: JSON object | null`.
`action.requested_effect` is always present. A `NARROWED` Decision also carries
`permitted_effect`; other Decision states require it to be `null`.

State strings use Core enum values:

- Decision: `admitted`, `held`, `narrowed`, `escalated`, `refused`;
- Adapter: `acknowledged`, `rejected`, `error`, `unknown`;
- Verification: `verified_bound`, `verified_no_bind`, `inconclusive`;
- Effect: `bound`, `no_bind`, `effect_unknown`.

`adapter_result.origin` is `adapter`, `sdk_recovery`, or `unspecified`.
`unspecified` supports legacy Core Warrants whose origin was not recorded; it
is not a third runtime origin state.

A decision-only portable Warrant has all five post-Decision records set to
`null`. If EffectProof exists, all five are objects. Partial combinations are
invalid.

## 20. Disclosure and validation rules

### 20.1 SUMMARY and FULL

`FULL` preserves supported Warrant business values and reference arrays.
`disclosure.omitted_fields` is empty.

`SUMMARY` sets the defined sensitive fields to `null` and lists each applicable
path in `omitted_fields`, including:

- `consequence.idempotency_key`;
- Principal, Agent, and Resource IDs;
- RequestedEffect parameters;
- `NARROWED` permitted-effect parameters;
- DecisionProof assurance-reference arrays; and
- adapter/verification/Effect reference arrays when those records exist.

Counts remain visible even when arrays are omitted.

SUMMARY is reduced disclosure, not anonymization. IDs, action types, states,
counts, and lineage can still be sensitive.

### 20.2 Consistency checks

Validation checks types, enum values, in-document ID links, canonical
Consequence/Action/Attempt relationships, state mappings, narrowed-effect
rules, verification-reference requirements, disclosure consistency, SDK
recovery provenance, and self-referential predecessor IDs.

A represented execution paired with an ineligible Decision may be reported as a
warning about the asserted path rather than rewritten into another Effect.
Decision and Effect remain independent.

Predecessor Warrants and Attempts are not embedded automatically. Unresolved
predecessor links are warnings, not proof of a complete history.

### 20.3 Parsing and compatibility

The reader rejects duplicate JSON keys, invalid UTF-8, non-finite numbers,
unknown or missing fields, unsupported versions, inconsistent lineage/state,
and undisclosed omissions.

Portable v1 is limited to:

```text
8 MiB UTF-8 JSON
nesting depth 64
```

Reader and writer apply the same limits and do not silently truncate records.

Changing the meaning or allowed structure of closed format v1 requires a new
format version and migration guidance.

v0.7 does not define cryptographic canonicalization, signatures, signer
identity, trust chains, or authenticity verification.

## 21. CLI contract

The installed entry point is `cage`.

```text
cage --help
cage --version
cage example database.delete [--warrant PATH]
cage example access.grant [--warrant PATH]
cage example payment.release [--warrant PATH]
cage warrant inspect PATH
cage warrant validate PATH
```

The examples use disposable local fixtures and the public SDK.

`--warrant` exports the final assurance snapshot using SUMMARY disclosure and
does not overwrite an existing file by default.

`inspect` prints lifecycle metadata without automatically printing business
payloads or reference contents.

`validate` reports structural validity and disclosure information. It does not
claim external-effect verification or cryptographic authentication.

| Exit code | Meaning |
| --- | --- |
| `0` | command completed; validation, when requested, found a structurally valid record |
| `1` | file access, example, or unexpected runtime failure |
| `2` | invalid arguments or invalid/unsupported portable record |

CLI exit `0` is not an Effect claim. A command may complete successfully while
the assurance state is `EFFECT_UNKNOWN`.

## 22. Compatibility and acceptance checks

The v0.7 implementation is expected to preserve all of the following:

- default IDs and deterministic custom factories work without production
  dependencies;
- invalid factories and known collisions fail before dispatch where possible;
- input helpers return the existing Core classes and preserve explicit
  identities;
- supported re-exports retain Core class identity;
- adapters, verifiers, and rules can use public imports only;
- facade orchestration preserves Core semantics and the documented local guards;
- SUMMARY and FULL preserve their promised fields, provenance, and omissions;
- Decision-only, narrowed, `EFFECT_UNKNOWN`, reconciled, and SDK-recovery
  records are representable;
- malformed portable records and size/depth violations fail in controlled ways;
- CLI commands and all three examples work from the installed distribution; and
- independent first-time-developer usability remains distinct from an
  author-run or automated rehearsal.

The 279-test result remains a historical v0.6 baseline, not evidence for v0.7.

## 23. Implementation history

This document began as the design contract for the v0.7 developer product.
Implementation then proceeded incrementally from identity/configuration through
the facade lifecycle, local guards, error recovery, input helpers, examples,
portable Warrants, CLI behavior, packaging, and release hardening.

The originally proposed interfaces in this document are now implemented except
where a section explicitly identifies a historical design name or future
capability.

The implementation deliberately kept the existing Core semantics intact rather
than replacing them with a second SDK-specific model.

Release tags, package publication, and historical test evidence remain separate
from this design record and are documented in the release-readiness and
changelog material.
