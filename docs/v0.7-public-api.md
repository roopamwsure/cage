## 1. Purpose and limits of this design step

Define the inputs, results, lineage responsibilities, failure recovery, and repeated-call behavior of four proposed facade methods: `evaluate`, `execute`, `verify`, and `reconcile`.

The signatures below originated as proposed interfaces. All four facade
methods are now available on the v0.7 feature branch; v0.6 did not expose
them. The facade delegates to the existing core.

Part 1 specifies method and result contracts. Part 2, in sections 9–14, adds
failure recovery and a facade-local dispatch guard. Part 3, in sections
15–22, describes configuration, supported imports, input helpers, portable
Warrants, and CLI contracts. Section 23 records the original first
implementation step; consult the implementation note above for current status.

## 2. Construction and ownership

Proposed constructor contract:

```text
CAGE(
    *,
    rule: EvaluationRule,
    config: CAGEConfig | None = None,
)
```

`rule` is required. It is the existing evaluation-rule callable, receiving the Attempt and tuples of Evidence, Standing, Delegation, Approval, and Context, and returning an `EvaluationOutcome`.

There is no default rule that admits an action. Generic CAGE does not infer which assurance facts are sufficient for a business operation. The supplied rule retains that responsibility.

The facade owns an in-memory `IdempotencyRegistry` for its lifetime. Reuse the same facade when relying on that registry. A separate facade or a restarted process does not inherit its history. v0.7 does not expose registry injection, state restoration, or a durable/distributed store through configuration.

The same facade owns the dispatch guard described below. Both pieces of state are local to that instance. Sharing a configuration or ID-factory object does not share execution history.

`config=None` selects the `CAGEConfig` defaults in section 15. No configuration option may bypass custody, capability validation, verification, or the dispatch guard.

## 3. Method contracts

### 3.1 Evaluate a consequential action

```text
evaluate(
    *,
    action: Action,
    idempotency_key: str,
    evidence: Sequence[Evidence] = (),
    standing: Sequence[Standing] = (),
    delegations: Sequence[Delegation] = (),
    approvals: Sequence[Approval] = (),
    context: Sequence[Context] = (),
    previous: EvaluationResult | None = None,
    ids: EvaluationIds | None = None,
) -> EvaluationResult
```

Required developer inputs are an existing `Action` and a stable business-operation `idempotency_key`. The assurance inputs remain typed sequences matching the core. A single Context is supplied as a one-item sequence; an arbitrary dictionary is not substituted for the existing Context contract.

The facade:

1. Validates its arguments and fixes the assurance-input sequences used for this evaluation.
2. Constructs a candidate Consequence and resolves it through `IdempotencyRegistry.resolve()`.
3. Creates an evaluation Attempt for the resolved Consequence.
4. Calls `evaluate_attempt()` with the configured rule and those assurance inputs.
5. Calls `create_decision_proof()` using that Decision and the same input snapshots.
6. Creates a decision-only Warrant and returns an `EvaluationResult`.

All Decision states are normal evaluation outcomes. A `REFUSED` Decision returns a result that can be inspected; it is not automatically an exception. The method never invokes an adapter or verifier and never creates an Effect.

If `previous` is supplied, this is an explicit evaluation replay. The action and key must resolve consistently with the previous Consequence. The facade uses `create_replay_attempt()` to create a new Attempt and links the new decision-only Warrant to `previous.warrant`. The rule receives the new assurance inputs. A conflicting request fails; replay does not silently become a new business consequence.

Without `previous`, the method does not invent a predecessor Attempt or claim to have found the latest Warrant. Repeated equivalent requests can resolve to the same Consequence while creating distinct evaluation Attempts.

### 3.2 Execute an evaluated consequence under custody

```text
execute(
    evaluation: EvaluationResult,
    *,
    adapter: EffectAdapter,
    capability: ExecutionCapability,
    execution_attempt_id: str | None = None,
) -> ExecutionResult
```

The input is the complete `EvaluationResult`, retaining its DecisionProof and Warrant. A bare Decision remains available to low-level users through the existing core; the facade does not require applications to reassemble missing proof context.

The facade creates an `ExecutionAttempt` for the exact Decision in the evaluation result and delegates to `execute_under_custody()`.

The existing custody function determines eligibility, selects the permitted effect, validates capability scope, invokes the adapter, and checks returned execution lineage. Those rules are not reimplemented in the facade.

`ADMITTED` selects the original requested effect. `NARROWED` selects the explicitly permitted effect. `HELD`, `ESCALATED`, and `REFUSED` fail before adapter invocation.

The caller supplies the capability. CAGE does not manufacture authority because evaluation admitted the action. The result exposes the resolved Consequence ID needed to obtain or construct the appropriate capability through the application's authority model.

An adapter-returned `ACKNOWLEDGED`, `REJECTED`, `ERROR`, or `UNKNOWN` is an execution observation carried in `ExecutionResult`. None of these states alone produces an Effect or EffectProof.

This method does not call a verifier or automatically retry execution. The proposed facade guard rejects another dispatch of the same canonical Consequence within the lifetime of that `CAGE` instance. This applies after a valid adapter result and after a failure where dispatch may have begun. The guard and recovery behavior are specified in sections 9–14. The existing core registry continues to resolve identity; it does not itself suppress adapter invocations.

### 3.3 Establish an assurance view from verification

```text
verify(
    execution: ExecutionResult,
    *,
    verifier: EffectVerifier,
    ids: AssuranceIds | None = None,
) -> AssuranceResult
```

The method observes the exact adapter result retained in `execution`.

The existing `reconcile_effect_verification()` helper already invokes a verifier and validates its returned adapter-result lineage. Despite its name, it does not require a previous verification, so the facade can also reuse it for the first verification without adding a second validation implementation.

The facade then uses `create_effect_from_verification()` and `create_effect_proof()` and constructs a Warrant with the original DecisionProof. This Warrant references the evaluation's decision-only Warrant as its predecessor.

The result preserves the existing mappings:

| Verification | Effect |
| --- | --- |
| `VERIFIED_BOUND` | `BOUND` |
| `VERIFIED_NO_BIND` | `NO_BIND` |
| `INCONCLUSIVE` | `EFFECT_UNKNOWN` |

Both conclusive verification states require references under the existing contract. An inconclusive result is a normal `AssuranceResult`, not an exception.

Verification does not execute the operation. To extend an existing assurance history after this step, use `reconcile` with the preceding `AssuranceResult`.

The current facade reserves first verification per execution within one
`CAGE` instance. A concurrent or later second `verify()` raises
`DuplicateVerificationError`. Its `execution` points to the original record;
its `assurance` is `None` while the first call is in progress, or the completed
`AssuranceResult` after success. A failed or interrupted verification releases
the reservation, so the caller may retry `verify()` with the same execution.
After success, later observations use `reconcile()` instead.

### 3.4 Reconcile an existing assurance view

```text
reconcile(
    previous: AssuranceResult,
    *,
    verifier: EffectVerifier,
    ids: AssuranceIds | None = None,
) -> AssuranceResult
```

`previous` contains both the prior Warrant and the original execution context. The caller does not need to recover an adapter result or rebuild proof references manually.

The facade reuses the original `AdapterExecutionResult` with `reconcile_effect_verification()`, then creates a new Effect, EffectProof, and Warrant. The new Warrant's `previous_warrant_id` is exactly `previous.warrant.warrant_id`.

Consequence, evaluation, execution, adapter-result, and DecisionProof lineage are retained. The new verification and new assurance records have new identities. Earlier objects are not modified.

The method takes no adapter or capability and does not create an ExecutionAttempt. It can remain inconclusive. Reconciliation is not restricted to converting uncertainty into certainty; the core does not promise that later observations will always be more conclusive.

Within one `CAGE` instance, a predecessor assurance Warrant has one reserved
successor. A concurrent or repeated `reconcile()` with the same predecessor
raises `DuplicateReconciliationError`. Its `previous` is the predecessor;
`assurance` is `None` while the first call is running, or the completed
successor afterward. A failure or interruption releases the reservation so
the caller can retry from that predecessor. To continue a successful chain,
pass the newly returned assurance to the next `reconcile()` call.

## 4. Typed result contracts

New result wrappers should be immutable. Use existing domain objects as their authoritative records and derive convenience properties from them. Avoid storing multiple independently editable copies of the same lifecycle fact.

| Proposed result | Authoritative contents | Read-only convenience access |
| --- | --- | --- |
| `EvaluationResult` | Decision-only `warrant: Warrant` | `decision`, `decision_proof`, `attempt`, `consequence`, `consequence_id`, `idempotency_key` |
| `ExecutionResult` | `evaluation: EvaluationResult`, `capability: ExecutionCapability`, `adapter_result: AdapterExecutionResult`, `observation_origin: ExecutionObservationOrigin` | `decision`, `decision_proof`, `execution_attempt`, `consequence_id`, `idempotency_key` |
| `AssuranceResult` | `execution: ExecutionResult`, `warrant: Warrant` containing an EffectProof | `decision`, `decision_proof`, `execution_attempt`, `adapter_result`, `observation_origin`, `verification`, `effect`, `effect_proof`, `consequence_id`, `idempotency_key` |

An `EvaluationResult` requires a Warrant with no EffectProof. An `AssuranceResult` requires a Warrant with an EffectProof. The wrappers validate that their records refer to the same complete lifecycle, including the Decision and ExecutionAttempt, rather than accepting matching consequence IDs alone as sufficient.

These checks keep the facade's own record assembly consistent. They do not turn Python objects or imported JSON into cryptographic authorization.

Before verification, there is no authoritative Effect in these results. This differs from an `AssuranceResult` containing `EFFECT_UNKNOWN` after inconclusive verification.

There is no generic `success` property. Developers inspect `decision.state`, `adapter_result.state`, `verification.state`, and `effect.state` for the fact they actually need.

`ExecutionObservationOrigin` has two proposed values: `ADAPTER` (`"adapter"`) and `SDK_RECOVERY` (`"sdk_recovery"`). It identifies who produced the execution observation, not who established the external Effect. The recovery origin must remain visible through verification, reconciliation, inspection, and export.

## 5. Identity defaults and explicit overrides

Two proposed override objects keep the common method calls small:

| Override object | Optional fields, each `str | None` |
| --- | --- |
| `EvaluationIds` | `consequence_id`, `attempt_id`, `decision_id`, `decision_proof_id`, `warrant_id` |
| `AssuranceIds` | `effect_id`, `effect_proof_id`, `warrant_id` |

Omitted fields receive generated identifiers. `execution_attempt_id` remains a direct optional parameter. An SDK recovery observation additionally needs a locally generated result ID; the configured ID factory must support deterministic generation for testing without changing or replacing an adapter-returned result ID.

ID ownership follows the existing contracts:

- The facade owns the IDs for the objects it creates.
- Existing `Action` and assurance inputs retain their supplied identities. The `cage.inputs` helpers in section 17 can generate their record IDs when constructing new inputs. Principal, Agent, and Resource identities remain caller-supplied references.
- An adapter owns the result ID of its returned `AdapterExecutionResult`. The facade owns the ID of an explicitly labelled SDK recovery observation when no usable adapter result exists.
- A verifier owns `EffectVerificationResult.verification_id`.
- Reference adapters and verifiers can generate their own record IDs by default. Custom integrations can supply meaningful IDs through their existing result constructors.
- The facade never silently replaces IDs returned by integrations.

An explicit `consequence_id` is the proposed ID for a new Consequence. When an existing idempotency key resolves to a previously established equivalent Consequence, that existing Consequence and its ID remain authoritative, matching the current registry. The returned result exposes the actual ID to use for capability scoping.

Replay and reconciliation must not reuse the immediate predecessor's event identities. Known conflicts must fail clearly. Section 15 defines the ID factory and local collision checks; neither provides a global uniqueness registry.

## 6. Why the idempotency key is required

**Recommendation: require a caller-supplied `idempotency_key` even though lifecycle IDs are automatic.**

The application chooses a key for one intended business operation and retains it when recovering or re-evaluating that operation. An intentionally different operation needs a different key, even if some parameters happen to be identical.

Randomly generating a fresh key on every evaluation would prevent the facade from recognizing repeated requests. Generating one by hashing effect parameters would risk conflating separate intended operations. CAGE therefore should not silently invent this business distinction.

Matching the same key and equivalent intent preserves Consequence identity within the registry's scope. It does not establish exactly-once execution, target-system idempotency, or cross-process coordination.

## 7. Evidence and error boundaries

Failures after possible dispatch retain the original execution identity and the context required for observation. They must not imply `NO_BIND`, generate a new consequence for recovery, or trigger an automatic retry.

The proposed recovery path supplies an explicitly labelled local execution observation when no usable adapter result exists. Only the separate verifier can subsequently establish an Effect. The SDK never invents a successful adapter acknowledgement or a successful verification.

Existing domain exceptions retain meaningful compatibility through the SDK hierarchy described in section 13. Error classification depends on where failure occurred, not simply the exception's class name.

## 8. Source mapping

| Responsibility | Existing v0.6 contract |
| --- | --- |
| Resolve equivalent business intent | `IdempotencyRegistry.resolve()` in `idempotency.py` |
| Create explicit replay lineage | `create_replay_attempt()` in `replay.py` |
| Evaluate supplied assurance inputs | `evaluate_attempt()` in `evaluation.py` |
| Capture input references | `create_decision_proof()` in `warrant.py` |
| Enforce custody and execute | `execute_under_custody()` in `custody.py` |
| Invoke verifier and check returned lineage | `reconcile_effect_verification()` in `verification.py` |
| Establish Effect from verification | `create_effect_from_verification()` in `verification.py` |
| Bind Effect to verification evidence | `create_effect_proof()` in `warrant.py` |
| Preserve assurance snapshots and predecessors | `Warrant` in `warrant.py` |

The facade adds orchestration and result assembly around these contracts. It must not copy their decision-state logic or Effect mappings into an independent engine.

## 9. Part 2 — One dispatch per Consequence within a facade instance

**Proposed default: once adapter dispatch may have begun for a Consequence, that `CAGE` instance will not dispatch it again.**

Repeated `execute()` calls raise `DuplicateExecutionError`. They do not call the adapter, silently return a cached success, or create another ExecutionAttempt representing an external invocation.

The guard uses the canonical Consequence established by the existing registry. A new evaluation Attempt, Decision, or proposed execution ID does not reset it. Known conflicts between a key and its canonical Consequence are rejected before dispatch.

The record remains consumed after:

- Any valid adapter outcome, including `REJECTED`, `ERROR`, or `UNKNOWN`.
- An adapter exception, invalid result, or mismatched result after possible dispatch.
- Verification resulting in `BOUND`, `NO_BIND`, or `EFFECT_UNKNOWN`.
- A verifier exception or failed result assembly.

Even verified `NO_BIND` does not automatically authorize or schedule another attempt. A future explicit execution-retry contract can address that use case. v0.7 has no `force`, retry loop, or reset option that clears this guard.

The guard covers facade dispatches in one live instance. It does not prevent multiple mutations inside a single adapter call, coordinate another `CAGE` instance, survive a restart, or govern direct low-level calls. Target systems and integrations still own their execution-idempotency mechanisms. Creating another key or runtime is not a documented retry procedure for the same business operation.

## 10. Dispatch tracking and concurrency

Maintain a small in-memory record for each guarded Consequence. This is SDK orchestration bookkeeping; it does not add or change core Decision, adapter, verification, or Effect states.

The required sequence is:

1. Validate SDK inputs and lifecycle consistency. Allocate the ExecutionAttempt and recovery-record identifiers before external dispatch so an ID-generation failure cannot strand an already-started operation.
2. Atomically reserve the canonical Consequence. A concurrent or re-entrant request for the same Consequence receives `DuplicateExecutionError` immediately.
3. Delegate to `execute_under_custody()`. A thin adapter wrapper records entry into the dispatch boundary immediately before calling the supplied adapter. It passes the exact ExecutionAttempt, selected effect, and capability received from custody.
4. If failure occurs and the supplied adapter could not have been invoked, release the reservation. Correcting the input and making another explicit call is allowed; no external Effect is inferred from this local failure.
5. Once the dispatch marker is set, retain the record regardless of outcome. Store the validated adapter result when available, or the recovery context described in section 11.

The original adapter must still be checked against its protocol; wrapping it must not hide an invalid adapter. Custody remains responsible for eligibility, selected-effect handling, capability validation, and result-lineage checks. The wrapper must not normalize an invalid return into apparent adapter success.

Record dispatch before attempting the adapter call. An adapter may fail before performing I/O, but CAGE cannot generally establish that from an exception. A conservative consumed record is preferable to an unsupported second invocation.

Registry resolution and dispatch reservations must be synchronized within the facade. In particular, two concurrent evaluations with the same key must not race into separate canonical Consequences. Do not hold the state lock while running the evaluation rule, adapter, or verifier; different Consequences should not be serialized behind a slow external call.

An adapter raising an exception named `CapabilityMismatchError` is still a callback failure after possible dispatch. Only a confirmed failure before the dispatch marker can release the reservation. Exception names alone cannot establish whether external mutation was possible.

## 11. Adapter failure and recoverable execution context

### 11.1 Valid adapter results remain normal outcomes

If the adapter returns a valid result with matching execution lineage, `execute()` returns an `ExecutionResult` with origin `ADAPTER`, regardless of its adapter state. An explicit adapter `ERROR` is therefore a typed outcome, while a Python exception escaping the adapter is an invocation failure.

### 11.2 No usable adapter result

For an ordinary adapter exception, invalid return type, or returned result belonging to another execution, the facade raises a typed execution error. Its `execution` attribute contains a recoverable `ExecutionResult` with the original evaluation, capability, and ExecutionAttempt.

To satisfy the existing verifier input contract, that result contains a locally created `AdapterExecutionResult` with:

- A distinct SDK-generated `result_id`.
- The original ExecutionAttempt; no replacement attempt or consequence.
- `AdapterExecutionState.UNKNOWN`.
- The diagnostic reference `urn:cage:sdk:recovery-observation`.
- `ExecutionResult.observation_origin = SDK_RECOVERY`.

This records that no usable adapter outcome is available. It does not assert that the adapter returned this result, that the external system accepted anything, or that an Effect has been established. The diagnostic reference is not authoritative external evidence.

If a valid, matching adapter result was already obtained before a later SDK assembly error, retain that original observation and its `ADAPTER` origin rather than replacing it with `UNKNOWN`.

Never repair a mismatched result by changing its execution ID or copying its claimed receipts onto the expected execution. Preserve the contract violation as an error and use the separate local recovery record for observation.

Prepare recoverable context before dispatch and retain it in the guard. Failures such as abrupt process death or unrecoverable memory exhaustion remain outside an in-memory recovery guarantee.

### 11.3 Recovery through the existing verification method

The recovery operation is `verify(error.execution, verifier=...)`. It uses the original execution context, does not dispatch again, and requires no fifth lifecycle method.

The verifier must be able to handle an unavailable receipt. It can use execution/consequence correlation and authoritative target-state evidence. If that is insufficient, it returns `INCONCLUSIVE`, yielding `EFFECT_UNKNOWN` through the existing core mapping.

A later `reconcile(previous_assurance, verifier=...)` re-observes that same SDK recovery record. The record is historical and remains labelled as SDK-produced even if external evidence later establishes `BOUND` or `NO_BIND`.

The recovery marker in the observation references and the explicit origin in the SDK result must survive portable inspection/export. No serializer may present this record as an adapter-issued acknowledgement. The marker is provenance metadata, not cryptographic authentication.

## 12. Verification failures and repeated observation

A verifier returning `INCONCLUSIVE` is a normal result. A verifier raising, returning the wrong type, or returning verification for another adapter result is an error.

Such an error retains the `ExecutionResult` and, for reconciliation, the previous `AssuranceResult`. It creates no replacement verification, Effect, EffectProof, or Warrant. In particular, the SDK must not invent an `INCONCLUSIVE` verification merely to make a failing callback look like a completed verification stage.

Recovery from an initial verification error is another explicit `verify()` using the retained execution. Recovery from a reconciliation error is another explicit `reconcile()` using the retained prior assurance. Neither path invokes the adapter. CAGE adds no polling or retry loop by default.

If a valid verification was obtained but later local proof/result assembly fails, retain that verification in the error context. Do not discard its evidence or claim that a new Warrant was successfully created.

Previously returned assurance records remain historical snapshots. A failed observation does not update their meaning or demonstrate that they describe current external state.

Ordinary callback failures are caught at their invocation boundary. Process-control signals such as `KeyboardInterrupt` and `SystemExit` propagate; they are not reported as completed adapter or verifier outcomes. Cleanup must not clear a consumed dispatch guard. A hard termination may lose all local state.

## 13. Proposed exception contracts

New public SDK exceptions share a `CAGEError` base. Normal Decision states, valid adapter states, and valid verification states do not become exceptions merely because they are unfavorable.

This table records the original design targets. Some proposed names were
refined during implementation and are not importable from the current SDK.

| Error category | Proposed public error | Required context or behavior |
| --- | --- | --- |
| Rule raises | `EvaluationRuleError` | Preserve the evaluation Attempt and original cause; no Decision or permission is fabricated |
| Rule returns an invalid outcome | `EvaluationContractError` | Identify the invalid rule contract; no execution |
| Invalid SDK argument | `CAGETypeError` or `CAGEValueError` | Preserve the corresponding built-in error category; fail before dispatch when relevant |
| Ineligible Decision | `CustodyIneligibleError` | Preserve existing core exception catch compatibility; adapter not invoked |
| Capability scope mismatch | `CapabilityMismatchError` | Preserve existing core exception catch compatibility; adapter not invoked |
| Conflicting idempotency key | `IdempotencyConflictError` | Preserve existing core exception catch compatibility; no replacement business intent |
| Repeated/in-progress dispatch | `DuplicateExecutionError` | Existing ExecutionAttempt, Consequence ID, and completed/recovery ExecutionResult when available |
| Adapter raises | `AdapterInvocationError`, under `ExecutionError` | `execution: ExecutionResult` for observation; original cause retained |
| Adapter returns an invalid type | `AdapterContractError`, under `ExecutionError` | Recoverable execution; do not treat the invalid return as a valid adapter result |
| Adapter returns another execution | `AdapterResultMismatchError`, under `ExecutionError` | Recoverable execution and existing core mismatch catch compatibility |
| Local assembly fails after dispatch | `ExecutionFinalizationError`, under `ExecutionError` | Original validated observation when available, otherwise the prepared recovery context |
| Verifier raises | `VerificationInvocationError`, under `VerificationError` | `execution`, optional `previous_assurance`, and original cause |
| Verifier returns an invalid type | `VerificationContractError`, under `VerificationError` | Same observation context; no invented verification |
| Verification refers to another result | `VerificationResultMismatchError`, under `VerificationError` | Same context and existing core mismatch catch compatibility |
| Proof/result assembly fails after valid verification | `AssuranceFinalizationError`, under `VerificationError` | Retain `verification` plus execution and prior-assurance context; no false completion |

Current implemented names include `AdapterInvocationError`,
`AdapterContractError`, `AdapterResultMismatchError`,
`DuplicateExecutionError`, `DuplicateVerificationError`,
`DuplicateReconciliationError`,
`VerifierInvocationError`, `VerifierContractError`,
`VerificationResultMismatchError`, and `AssuranceAssemblyError`. The four
verifier/assurance errors inherit `ExecutionError` and retain `execution`;
reconciliation errors also retain `previous`.
`AssuranceAssemblyError` additionally retains the valid `verification` and
the failed `stage`. The proposed `EvaluationRuleError`,
`EvaluationContractError`, `ExecutionFinalizationError`, `VerificationError`,
`VerificationInvocationError`, `VerificationContractError`, and
`AssuranceFinalizationError` are not exported by the current SDK. Consult
`src/cage/errors.py` for the implemented classes.

SDK counterparts for existing core domain exceptions should subclass the corresponding core exception as well as their SDK error family. Code catching the original core class must continue to catch the facade counterpart. Existing core classes and their direct-call behavior remain unchanged. A direct low-level exception is not promised to inherit the new SDK base.

`ExecutionError.execution` is required whenever an ordinary failure occurred after possible dispatch. A duplicate request does not create a new execution failure: its error points to the original attempt. If that attempt is still running, a completed ExecutionResult may not yet be available; the caller obtains the outcome from the original invocation.

Messages must distinguish local validation, adapter contract failure, unknown external outcome, and failed observation. Preserve causes for controlled debugging, but SDK-provided formatting and CLI output must not automatically print provider payloads, credentials, or raw exception messages. Application-generated tracebacks and logs require their own handling.

## 14. Required behavioral checks for implementation

These are acceptance scenarios for future implementation, not newly executed tests.

| Scenario | Required outcome |
| --- | --- |
| Refused Decision or mismatched capability | Adapter called zero times; correct validation error; no claimed Effect |
| Corrected request after confirmed pre-dispatch failure | An explicit subsequent call can reach custody; no permanent guard from the failed validation |
| Same Consequence executed twice | Adapter called at most once through this facade; second call raises `DuplicateExecutionError` |
| Replay produces a new admitted Decision after dispatch | Same Consequence remains guarded; new evaluation does not enable another dispatch |
| Two threads evaluate the same key and try to execute | One canonical Consequence and at most one adapter dispatch through this facade |
| Adapter mutates target and then raises | Recovery error retains original context; independent verification can establish `BOUND`; no second dispatch |
| Adapter raises before an observable mutation | No inferred `NO_BIND`; verifier must establish external reality |
| Adapter raises a core-named validation exception | Classified as an invocation failure after dispatch; guard retained |
| Adapter returns malformed or mismatched data | Contract error plus clearly labelled local recovery observation; no relabelling of the returned receipt |
| Adapter returns valid `REJECTED` or `ERROR` | Normal execution result, no automatic Effect, and no automatic re-dispatch |
| Recovery observation reaches a verifier without enough evidence | `INCONCLUSIVE` becomes `EFFECT_UNKNOWN`; no stronger claim |
| Verifier raises or returns mismatched lineage | No new Effect or Warrant; original context remains usable for another observation |
| Reconciliation resolves uncertainty | New Warrant links to the previous Warrant; adapter call count unchanged; SDK recovery origin retained if applicable |
| Reconciliation returns `NO_BIND` | New assurance snapshot; dispatch guard remains consumed |
| A different facade or process is used | Documentation does not claim shared dispatch protection or restart recovery |

The full regression suite remains required when implementation begins. No implementation or extra test run is justified merely by this document update.

## 15. Part 3 — Minimal configuration and identity generation

`CAGEConfig` is immutable and has one configurable field:

| Field | Type | Default |
| --- | --- | --- |
| `id_factory` | `IdFactory` | `uuid_id` |

`IdFactory` is the callable contract `(kind: IdentityKind) -> str`. `uuid_id` uses the Python standard library to return `<kind.value>_<uuid4 hex>`. Callers treat the complete string as opaque. There is no runtime dependency added for identifiers or configuration.

`IdentityKind` is a string enum with the following member/value pairs:

| Member | Value | Typical owner |
| --- | --- | --- |
| `ACTION` | `action` | Input helper |
| `CONSEQUENCE` | `consequence` | Facade |
| `ATTEMPT` | `attempt` | Facade |
| `DECISION` | `decision` | Facade |
| `DECISION_PROOF` | `decision_proof` | Facade |
| `EXECUTION_ATTEMPT` | `execution_attempt` | Facade |
| `ADAPTER_RESULT` | `adapter_result` | Adapter or SDK recovery observation |
| `VERIFICATION` | `verification` | Verifier |
| `EFFECT` | `effect` | Facade |
| `EFFECT_PROOF` | `effect_proof` | Facade |
| `WARRANT` | `warrant` | Facade |
| `EVIDENCE` | `evidence` | Input helper |
| `STANDING` | `standing` | Input helper |
| `DELEGATION` | `delegation` | Input helper |
| `APPROVAL` | `approval` | Input helper |
| `CONTEXT` | `context` | Input helper |

Factories must return nonblank strings. The SDK does not silently trim, repair, retry, or replace invalid output. Invalid configuration types or noncallable factories raise `CAGETypeError`; invalid generated values raise `CAGETypeError` or `CAGEValueError` according to the violation. A factory that raises produces `IdentifierGenerationError`, under `CAGEError`, retaining the requested identity kind and original cause. The facade must not invoke the adapter after an ID-generation failure before dispatch.

The facade checks known record-ID conflicts within its lifetime, including explicit overrides. Reusing an existing record reference is allowed; assigning its identity to a different record is not. Resolving an equivalent Consequence through the existing registry is also allowed. Identity namespaces remain distinct: a Principal ID is not confused with an Action ID merely because their strings match.

Known conflicts detected before dispatch raise `IdentityConflictError`, a `CAGEValueError`. Conflicting IDs in integration output after dispatch or during verification are contract failures with the recovery context defined above. The SDK cannot detect an unseen conflict in another runtime or an external history store.

Custom factories used by concurrent callers must be thread-safe. The facade validates their output and local identity bindings; it does not infer safety from a custom factory's name. User callbacks are not invoked while holding the facade's state lock.

The facade exposes read-only `config: CAGEConfig` and `inputs: CAGEInputs` properties. All its input helpers use the configured factory and the same local identity checks. Reference adapters/verifiers accept an optional `id_factory` at their own construction, defaulting to `uuid_id`, so deterministic tests can control their record IDs too.

New facade-created Warrants use `schema_version="0.7"`. This is a documented core-record label, independent of package patch versions and the portable format version below. It is not a user-selectable claim of cryptographic protection.

There are no environment-file loaders, global registries, clock services, implicit network settings, execution-retry settings, or safety-disable switches in `CAGEConfig` for v0.7.

## 17. Input helpers and the Quickstart

`cage.inputs` constructs existing immutable core objects. It generates record IDs where omitted, then delegates field validation and JSON-value freezing to the existing constructors. It preserves explicit IDs.

All helper parameters are keyword-only. Their exact proposed signatures are:

```text
cage.inputs.action(
    *, action_type: str, principal_id: str, agent_id: str,
    resource_id: str, requested_effect: Mapping[str, object],
    action_id: str | None = None,

cage.inputs.evidence(
    *, evidence_type: str, subject: str, source: str,
    data: Mapping[str, object], evidence_id: str | None = None,

    *, standing_type: str, subject: str, source: str,

    *, delegator: str, delegatee: str, source: str,

    *, context_type: str, source: str,
    values: Mapping[str, object], context_id: str | None = None,

```

The action helper constructs Principal, Agent, Resource, and RequestedEffect using the supplied values. Principal/agent/resource IDs identify the supplied subjects; they are not generated substitutes for authenticated identity. No helper issues an ExecutionCapability or makes an approval fact trustworthy. Supplied evaluation logic still interprets assurance facts and their sources.

Developers already holding core objects pass them directly to the facade. They do not have to convert them through helpers.

The lead Quickstart uses `database.delete` against a disposable SQLite fixture and a supplied, readable evaluation rule. Its capability is explicitly scoped to that fixture and the evaluated Consequence. It shows the four lifecycle concepts using the actual public API and prints the Decision, adapter outcome, verification, Effect, and Warrant ID.

The installed examples must include all fixture setup, the rule, adapter, verifier, capability construction, expected output, and cleanup. No example may contain undefined placeholder integrations and be described as runnable. Example helpers are teaching assets, not another production integration framework.

`access.grant` demonstrates a narrowed effect in a local access-record fixture. `payment.release` uses a simulated ledger to demonstrate unavailable acknowledgement/observation and later reconciliation. A later verification can gain visibility of a change already made by the single execution; the verifier must not mutate the target to make its claim true.

The 15-minute acceptance check starts with documented Python prerequisites and the built release package. Documentation must not claim a PyPI package is available before the actual distribution has been verified. Until publication, installation instructions use the release wheel or the documented source-development route.

## 18. Portable Warrant API

Portable records are detached inspection data. Parsing them does not reconstruct a live EvaluationResult, ExecutionResult, capability, dispatch guard, or authorization to execute.

`WarrantDisclosure` is a string enum: `SUMMARY="summary"`, `FULL="full"`. The default is `SUMMARY`.

```text
export_warrant(
    source: Warrant | EvaluationResult | AssuranceResult,
    *, disclosure: WarrantDisclosure = WarrantDisclosure.SUMMARY,
) -> PortableWarrant

parse_warrant(data: str | bytes) -> PortableWarrant

load_warrant(path: str | Path) -> PortableWarrant

dump_warrant(
    document: PortableWarrant, path: str | Path,
    *, overwrite: bool = False,
) -> None

validate_warrant(
    data: str | bytes | PortableWarrant,
) -> WarrantValidationReport
```

`PortableWarrant` is immutable and exposes typed read-only properties: `format_version`, `disclosure`, `warrant_id`, `schema_version`, `consequence_id`, `decision_state`, `effect_state`, `execution_attempt_id`, `previous_warrant_id`, and `observation_origin`. Effect/execution properties are `None` when their records are absent. An unspecified observation origin is also `None`, distinguishable using the presence of the execution record.

It also provides `to_dict() -> dict[str, object]`, returning a fresh JSON-compatible copy, and `to_json(*, indent: int | None = 2) -> str`. Formatting choices do not promise cryptographic canonicalization or stable signed bytes. Integer indentation from 0 through 8, or `None`, is supported.

`export_warrant()` verifies lifecycle consistency before projecting source objects. A facade result supplies its explicit observation origin. For a bare core Warrant, the reserved SDK recovery marker establishes the recorded recovery label; otherwise origin is `unspecified`, because the core Warrant has no separate origin field. It must never guess `adapter` merely from the Python class name.

Portable v1 represents one internally consistent decision/execution path. A raw Warrant joining differing Decisions or inconsistent action/attempt records is rejected with an actionable export error, even if a low-level constructor accepted it. The exporter does not silently flatten multiple paths into one claim. Direct core behavior remains unchanged.

`ExecutionResult` is not a Warrant and is not an accepted export source. Its evaluation Warrant can be exported as a decision-only record. Persisting an in-progress execution context for restart recovery is outside this format.

`load_warrant()` and `dump_warrant()` use UTF-8 files and do not create parent directories implicitly. Dump refuses an existing path unless `overwrite=True`; validation/serialization must complete before replacing an existing destination. File failures raise `WarrantIOError` without affecting runtime execution state.

An application can export its completed `AssuranceResult` and inspect it later:

```python
from cage.warrants import dump_warrant, export_warrant, load_warrant, validate_warrant

document = export_warrant(assurance)  # SUMMARY is the default disclosure
dump_warrant(document, "assurance-warrant.json")
detached = load_warrant("assurance-warrant.json")
report = validate_warrant(detached)
assert report.structurally_valid
```

The example assumes `assurance` comes from a completed `CAGE.verify()` or
`CAGE.reconcile()` call. The file contains inspection data and cannot be used
as an execution capability. Keep FULL-disclosure files private if they
contain business data or references.

Additional public exceptions are `IdentifierGenerationError` under `CAGEError`; `IdentityConflictError`, `WarrantExportError`, and `WarrantFormatError` under `CAGEValueError`; `UnsupportedWarrantVersionError` under `WarrantFormatError`; and `WarrantIOError` under both `CAGEError` and `OSError`. Parse raises on invalid data. Validate returns a report with `structurally_valid: bool`, `disclosure: WarrantDisclosure | None`, and `issues: tuple[ValidationIssue, ...]`; it does not raise for malformed record content. Invalid API argument types still raise `CAGETypeError`.

Each ValidationIssue has `severity` (`"error"` or `"warning"`), a stable `code`, a field `path`, and a safe `message`. Structural validity means that the representation satisfies this format. It does not establish authenticity, evidence truth, or current external state.

## 19. Portable Warrant format v1

The envelope uses `format="cage.warrant"` and `format_version="1"`. Both values are required strings. The native Warrant's `schema_version` is preserved separately as record metadata; it is not used to select the JSON parser or infer authenticity.

Every top-level key in the table below is required. There are no unspecified extension fields in format v1. Object field names are exact; identifiers are nonblank strings unless explicitly nullable. References are ordered arrays of nonblank strings. Counts are nonnegative integers, not booleans.

| Top-level field | Exact contents |
| --- | --- |
| `format` | Literal `"cage.warrant"` |
| `format_version` | Literal `"1"` |
| `disclosure` | `profile: "summary" or "full"`; `omitted_fields: array[string]` of the defined field paths |
| `warrant` | `warrant_id`, `schema_version`, `previous_warrant_id: string or null` |
| `consequence` | `consequence_id`, `action_id`, `idempotency_key: string or null` |
| `action` | `action_id`, `action_type`, `principal_id`, `agent_id`, `resource_id`, `requested_effect`; the three subject/resource IDs are nullable only in summary |
| `evaluation_attempt` | `attempt_id`, `consequence_id`, `previous_attempt_id: string or null` |
| `decision` | `decision_id`, `attempt_id`, `state`, `permitted_effect: EffectData or null` |
| `decision_proof` | `proof_id`, `decision_id`, `evidence_refs`, `standing_refs`, `delegation_refs`, `approval_refs`, `context_refs`, `reference_counts` |
| `execution_attempt` | Object or null; object fields: `execution_attempt_id`, `decision_id`, `previous_execution_attempt_id: string or null` |
| `adapter_result` | Object or null; object fields: `result_id`, `execution_attempt_id`, `state`, `origin`, `references`, `reference_count` |
| `verification` | Object or null; object fields: `verification_id`, `adapter_result_id`, `state`, `references`, `reference_count` |
| `effect` | Object or null; object fields: `effect_id`, `consequence_id`, `state`, `verification_refs`, `verification_ref_count` |
| `effect_proof` | Object or null; object fields: `proof_id`, `effect_id`, `verification_id` |

`EffectData` is exactly an object with `parameters: JSON object or null`. `action.requested_effect` is always an EffectData object. A NARROWED Decision also has an EffectData object in `permitted_effect`; other Decision states require `permitted_effect=null`. Redaction changes `parameters` to null, not the existence of the permitted-effect object.

`decision_proof.reference_counts` is exactly an object with `evidence`, `standing`, `delegation`, `approval`, and `context` integer fields. The five corresponding reference-array fields may be null only in summary. All other `references`/`verification_refs` fields follow the same array-or-summary-null rule.

State strings use existing core enum values:

- Decision: `admitted`, `held`, `narrowed`, `escalated`, `refused`.
- Adapter: `acknowledged`, `rejected`, `error`, `unknown`.
- Verification: `verified_bound`, `verified_no_bind`, `inconclusive`.
- Effect: `bound`, `no_bind`, `effect_unknown`.

`adapter_result.origin` is `adapter`, `sdk_recovery`, or `unspecified`. The last value supports a bare legacy core Warrant whose origin was not recorded. It is not a third runtime execution-origin state.

A decision-only Warrant has all five of `execution_attempt`, `adapter_result`, `verification`, `effect`, and `effect_proof` set to null. If an EffectProof exists, all five are objects. Partial combinations are invalid in v1. Null EffectProof does not mean `NO_BIND` or `EFFECT_UNKNOWN`.

## 20. Disclosure and validation rules

### 20.1 Summary and full views

FULL preserves the supported Warrant's action parameters, subject/resource IDs, business key, and reference arrays. `disclosure.omitted_fields` is empty. It does not include credentials from adapter objects, capability objects, evaluation-rule code, or assurance-input payloads that the native Warrant never contained. User-supplied Warrant values themselves may still be sensitive.

SUMMARY sets exactly these fields to null and lists each applicable path in `omitted_fields`:

- `consequence.idempotency_key`.
- `action.principal_id`, `action.agent_id`, `action.resource_id`.
- `action.requested_effect.parameters`.
- `decision.permitted_effect.parameters`, only for a NARROWED Decision.
- The five reference-array fields under `decision_proof`.
- `adapter_result.references`, `verification.references`, and `effect.verification_refs`, only when those records exist.

Counts are retained, even when an omitted array was empty. The omission list has no duplicates and must exactly match the applicable profile fields. Other fields may not be silently dropped or redacted in v1. FULL nulls in required business-data/reference fields are invalid.

Summary is a disclosed inspection view, not a complete serialization of the underlying business evidence. Lifecycle IDs, action type, and states remain visible and can themselves be sensitive if callers chose identifying values. Neither profile promises anonymization or automatic secret detection.

### 20.2 Required consistency checks

Validation checks field types and enum values, all in-document ID links, the canonical consequence/action/evaluation path, and the relationship between Decision, execution, verification, Effect, and proof records.

It must also check:

- The Decision's narrowed-effect presence rule.
- A represented execution paired with an ineligible Decision produces a warning about the asserted execution path. It does not coerce the Effect or make a structurally consistent record unrepresentable merely because it describes a possible control violation. Decision and Effect remain independent.
- Verification and Effect states agree with the existing three mappings.
- Conclusive verification has a positive reference count; FULL also has the required nonempty array.
- FULL counts equal array lengths and Effect verification references exactly match verification references, preserving order and duplicates.
- SUMMARY corresponding verification/Effect counts agree, while reporting that hidden reference contents cannot be compared.
- An SDK recovery observation has adapter state `unknown`. FULL retains the reserved recovery marker. SUMMARY retains `origin=sdk_recovery` even though the reference array is omitted.
- A FULL observation carrying the reserved recovery marker is not labelled as an adapter-issued observation.
- Immediate predecessor IDs do not self-reference their current record.

These are checks on the consistency of a recorded claim. They do not create an authoritative Effect or contact the target system.

Predecessor Warrants, Attempts, and execution attempts are not bundled by v1. Report unresolved predecessor links as warnings. Never imply that a single file supplies or authenticates a complete history.

### 20.3 Parsing and format compatibility

Reject duplicate JSON keys, nonfinite numbers, invalid UTF-8, unknown fields, unsupported format versions, wrong types, and undisclosed omissions. Preserve supported integer values without silently rounding them. Decode to detached data; do not evaluate strings, import modules, instantiate runtime capabilities, or execute callbacks.

For v1, input and serialized output are limited to 8 MiB of UTF-8 JSON and nesting depth 64, counting the root container as depth 1. Report limits as format/export errors. The same limits apply to both reader and writer, and no record may be silently truncated to fit. A parser recursion failure must become a controlled format error.

Frozen core mappings and tuples are explicitly converted to JSON objects and arrays. Do not rely on dumping Python object dictionaries, object repr strings, or private attributes. Reading a PortableWarrant and serializing it again preserves supported content and disclosure metadata, not byte-for-byte formatting.

Changing the meaning or allowed structure of closed format v1 requires a new format version and migration guidance. Package patch updates must not silently reinterpret existing files. Cryptographic canonicalization, hashing profiles, signatures, key identities, and authenticity verification remain later-release work.

## 21. CLI contract

The installed entry point is `cage`. Its v0.7 commands are:

```text
cage --help
cage --version
cage example database.delete [--warrant PATH]
cage example access.grant [--warrant PATH]
cage example payment.release [--warrant PATH]
cage warrant inspect PATH
cage warrant validate PATH
```

Examples operate on disposable local fixtures, invoke the public SDK, and require no accounts or credentials. `--warrant` exports the final assurance snapshot with SUMMARY disclosure to the requested path; it does not overwrite an existing file. The exported predecessor links are not an embedded history bundle.

Inspect prints IDs, lifecycle states, disclosure profile, observation origin, and unresolved-lineage information. It does not print business payloads automatically, even when reading a FULL file. Validate reports structural validity and disclosed omissions; it must not describe the command as external-effect or cryptographic verification.

| Exit code | Meaning |
| --- | --- |
| `0` | Command completed; validation, when requested, found a structurally valid record |
| `1` | File-access failure, unexpected runtime failure, or example unable to complete its documented scenario |
| `2` | Invalid CLI arguments or invalid/unsupported portable record |

Exit code 0 is not a claim that a business Effect is BOUND. An example intentionally demonstrating uncertainty can complete successfully while displaying `EFFECT_UNKNOWN`. Safe error messages go to stderr; the CLI does not print raw provider tracebacks by default.

## 22. Compatibility and design acceptance checks

Implementation must demonstrate the following in addition to section 14 and the product release gates:

- Default IDs and deterministic custom factories work without a production dependency; invalid factories and known collisions fail before external dispatch where applicable.
- Every input helper returns the existing core class, preserves explicit identities, and uses the existing validation/freeze semantics.
- Supported re-exports have the same class identity as their core counterparts.
- Adapter, verifier, and evaluation-rule implementations need no private imports.
- Facade execution paths retain the existing regression behavior and new local guard/recovery rules without rewriting core semantics.
- SUMMARY and FULL records preserve their promised content, identities, states, observation provenance, and omission information through export and readback.
- Decision-only, narrowed, unknown-effect, reconciled, and SDK-recovery records all have representative portable-format fixtures.
- Malformed records, duplicate keys, unsupported versions, lineage mismatches, contradictory state pairs, redaction mismatches, and input-size/depth violations produce controlled validation outcomes.
- CLI commands and all three examples work from the installed wheel, outside the source checkout, including Windows/PowerShell instructions.
- A first-time developer completes the complete local Quickstart within the agreed time target; successful scripting alone does not establish that usability result.

The existing 279-test result is the verified v0.6 baseline, not evidence that any proposed v0.7 behavior is implemented. All future implementation claims require their own checks.
