# CAGE v0.7 — Developer Product

Status: Proposed architecture for review; not an approved API specification.

Date: 2026-09-19

Intended repository path: `docs/v0.7-developer-product.md`

Product: CAGE — Assurance Runtime for Consequential AI Actions

## 1. Baseline and design boundary

The supplied project handover records CAGE v0.6.0 — Consequence Custody as complete: package `cage-assurance 0.6.0`, 279 passing tests, all 33 release gates satisfied, and an annotated release tag pointing to commit `476c4930a909a593cfa8f55e92b390d3811578f7`.

These are handover facts. This draft does not claim a fresh inspection of the private repository, its tag, or its test results.

v0.6 provides the semantic core and custody engine. v0.7 makes that engine approachable through a supported SDK, useful local examples, portable records, and clear documentation. Its design must preserve existing semantics. Any concrete defect discovered during source review is handled explicitly and separately from convenience work.

This document proposes product requirements and boundaries. Exact method signatures, import paths, type names, exception names, configuration fields, and serialized field definitions follow in the public API design. Implementation begins after both design stages are agreed.

## 2. Product goal and problem statement

**A developer unfamiliar with CAGE should be able to install it and protect a first consequential action in less than 15 minutes.**

The first experience must demonstrate a complete lifecycle: describe an action, evaluate it, execute an eligible consequence under custody, establish its external effect, and inspect the resulting Warrant. It must also make clear that permission, execution acknowledgement, and effect are different facts.

Today, the semantic model exposes many concepts that are valuable for assurance but expensive to assemble manually. The adoption problem is the amount of orchestration a developer must understand before using the model correctly.

v0.7 should automate identifiers and lifecycle bookkeeping while leaving consequential choices explicit. Applications retain ownership of their business operations and external systems. CAGE supplies the assurance boundary around those operations.

The under-15-minute target applies to the supplied local Quickstart with documented Python prerequisites. It does not promise that a production integration, its credentials, or its verification design can be completed in that time.

## 3. Developer personas and priority

| Persona | Primary job | v0.7 experience |
| --- | --- | --- |
| Application developer — primary | Protect an existing consequential operation | Small facade, clear inputs, useful results, and an obvious path through uncertainty |
| Platform / AI infrastructure engineer | Embed CAGE in an existing platform | Supported contracts, explicit configuration and identity control, inspectable lifecycle, and lower-level access |
| Adapter / integration developer | Connect execution and verification to a target system | Public extension contracts, capability rules, local references, and focused conformance examples |
| Security / assurance engineer | Explain what was permitted, attempted, and established | Decisions, verification outcomes, Effects, proof references, Warrants, and reconciliation history |

The application developer determines the default path. Other personas receive deeper access without requiring every first-time user to understand every internal object.

## 4. Developer journey

| Stage | Developer responsibility | CAGE responsibility | Visible outcome |
| --- | --- | --- | --- |
| Install | Install the package in a supported environment | Provide complete distribution metadata and entry points | Working import and CLI |
| Describe | Identify the action, resource, requested effect, and required assurance inputs | Validate supported inputs and establish lifecycle identity | Traceable proposed consequence |
| Evaluate | Supply the assurance information required by the existing evaluator | Delegate evaluation and proof construction to existing contracts | Decision, explanation, identifiers, and DecisionProof |
| Execute | Supply an adapter and appropriately scoped capability | Enforce eligibility and custody through the existing engine | ExecutionAttempt and adapter outcome |
| Verify | Supply a verifier for the target system | Delegate verification and Effect/proof construction | Verification outcome, Effect, and Warrant as supported by the lifecycle |
| Inspect | Read the result or portable record | Preserve distinctions and lineage | What was decided, attempted, and established |
| Reconcile when needed | Request another observation of an unresolved consequence | Reuse the observation-only reconciliation path | New verification and Warrant lineage without re-execution |

Progressive disclosure has three levels:

1. **Use CAGE:** work through the facade and a reference integration.
2. **Understand CAGE:** inspect lifecycle objects, explanations, and lineage.
3. **Extend CAGE:** implement adapters and verifiers or use supported semantic APIs directly.

The first Quickstart follows the normal successful path. An adjacent example shows an acknowledgement followed by inconclusive verification and later reconciliation. This second path is essential to understanding the product.

## 5. Semantic invariants

The following distinctions remain binding:

- `Decision != Effect`
- `EvaluationAttempt != ExecutionAttempt`
- `Replay != execution retry`
- `Adapter result != Effect`
- `Execution != Verification`
- `Reconciliation != re-execution`
- `ADMITTED != BOUND`
- `REFUSED != NO_BIND`

The facade must preserve the existing state vocabulary and transitions:

| Existing state or observation | Required facade behavior |
| --- | --- |
| `ADMITTED` | Select the originally requested effect for custody |
| `NARROWED` | Select the explicitly permitted effect; never substitute the broader original request |
| `HELD`, `ESCALATED`, or `REFUSED` | Prevent crossing the custody boundary; do not infer an external Effect |
| Adapter `ACKNOWLEDGED` | Record the acknowledgement; require verification before declaring `BOUND` |
| Adapter `REJECTED`, `ERROR`, or `UNKNOWN` | Preserve the execution outcome; do not infer `NO_BIND` from it alone |
| `VERIFIED_BOUND` | Use the existing verification-backed path to establish `BOUND` |
| `VERIFIED_NO_BIND` | Use the existing verification-backed path to establish `NO_BIND` |
| `INCONCLUSIVE` | Preserve `EFFECT_UNKNOWN` |
| Later reconciliation | Observe again and extend lineage without invoking execution |

Before verification, a result must communicate that the effect has not been established. The convenience layer must not invent a new core Effect state to describe its own workflow progress.

## 6. Public API philosophy and facade

The proposed `CAGE` facade orchestrates the existing engine. It does not implement another evaluator, custody policy, verifier, or Effect transition system.

Its conceptual responsibilities are **evaluate, execute under custody, verify, reconcile, and expose results**. These are responsibilities, not finalized method signatures. Source inspection must establish how each maps to existing entry points; this document does not require splitting or rewriting current custody functions.

Principles:

- Provide one documented default path through the lifecycle.
- Generate ordinary lifecycle objects automatically where the existing contracts permit it.
- Keep required authority, evidence, capabilities, and external verification explicit.
- Preserve advanced access to supported low-level contracts.
- Prefer typed results over unstructured dictionaries.
- Keep operation identities and lineage available without requiring manual construction.
- Use actionable domain errors for developer mistakes.
- Keep cloud, agent-framework, policy-engine, and business-domain choices outside the core.

A convenience constructor must not invent approval, mint authority, or silently admit an action when required assurance inputs are absent. There is no catch-all “success” flag that merges permission, execution, and Effect.

An all-in-one execution shortcut is not required for v0.7. Any later shortcut must retain the same observable stages and safety contracts.

## 7. Supported and internal APIs

| Surface | Supported use | Boundary |
| --- | --- | --- |
| High-level SDK | Normal application integration | Small facade, configuration, inputs, results, and exceptions |
| Extension API | Adapter and verifier implementation | Public contracts and the types necessary to implement them |
| Low-level semantic API | Advanced orchestration and inspection | Existing supported core contracts and documented invariants |
| Internal implementation | SDK orchestration details | No external compatibility promise |

The public API design must provide an explicit export list and map it to the current source. Examples must use supported imports. An adapter or verifier author must not need private modules.

No repository-wide rename or relocation is justified merely to make the new facade look cleaner. Preserve documented v0.6 imports and behavior by default. Classify existing exports before changing their support status.

## 8. Identity strategy

Common use receives automatically generated identities wherever current contracts allow them. Advanced integrations can supply explicit identities through a documented route.

Identity rules:

- A Consequence identifies the intended business consequence across its related lifecycle.
- A new evaluation attempt and a new execution attempt remain different identities.
- Observations, proofs, and Warrants retain the identity and lineage distinctions defined by the core.
- Reconciliation retains the relevant consequence and execution references and creates the history entries required by the existing model.
- Overrides must satisfy existing format, consistency, and idempotency rules.
- Known conflicting reuse must be rejected within the scope of the available history.
- IDs are correlation mechanisms; knowing or choosing an ID does not grant authority.

**Fresh IDs do not prevent duplicate business effects.** Applications must preserve the appropriate consequence identity and existing idempotency information when recovering the same operation. Repeating a high-level call with new defaults must not be advertised as safe retry behavior.

Document the actual scope and lifetime of any retained history. v0.7 does not introduce a durable distributed store, restart recovery, or cross-process exactly-once guarantee. A portable Warrant alone is not a resumable execution context.

## 9. Configuration

Provide a small typed configuration model with documented defaults. Limit it to demonstrated SDK needs, such as identity generation and any dependencies the facade genuinely needs to orchestrate the existing engine.

Configuration must not:

- Disable custody or capability checks.
- Convert adapter acknowledgement into a verified Effect.
- Treat uncertainty as success or as evidence that nothing happened.
- Add automatic execution retries.
- Introduce accounts, telemetry, vendor defaults, remote plugin discovery, or a new policy language.

Unsupported or contradictory configuration must fail before it can cause an external operation. Precise fields and dependency ownership are API-design decisions, not an invitation to build a configuration framework.

## 10. Result objects and exceptions

Results should let a developer inspect these facts independently:

| Result area | Information to expose where available |
| --- | --- |
| Evaluation | Decision, permitted effect, explanation, identifiers, and DecisionProof |
| Execution | ExecutionAttempt, capability scope, adapter state, and diagnostics |
| Verification | Verification outcome, established Effect, evidence references, and EffectProof |
| Assurance history | Warrant and predecessor/related lifecycle references |

Results must distinguish information that is absent because a stage has not run from information that is inconclusive. New SDK result containers should preserve stable snapshots or references according to the existing model; callers must not be able to widen an authorization by editing a convenience result.

Propose one public CAGE exception root with meaningful categories for invalid input, invalid configuration or identity, custody ineligibility, capability mismatch, lifecycle misuse, and unsupported portable data. Exact class names follow source review.

The existing example `CustodyIneligibleError` captures the desired quality: “Decision REFUSED cannot cross the consequence-custody boundary.”

Expected domain outcomes remain typed outcomes. A refused evaluation or inconclusive verification is not automatically an exception. Attempting an operation that is invalid for that outcome should produce a useful error.

An error after external execution may have started must not erase attempt identity or imply `NO_BIND`. Preserve diagnostics needed for observation and reconciliation. Do not wrap every failure in a generic error that discards this context.

## 11. Adapter and verifier experience

An adapter performs the selected effect against a target system under the existing capability and custody contracts. A verifier establishes the external effect through the existing verification contract.

For each contract, documentation must explain inputs, outputs, scope checks, error handling, identifiers, and responsibilities. Reference implementations must be readable enough to serve as templates and must use public imports.

Verification must use evidence from the target system appropriate to the claimed consequence. Merely repeating the adapter's returned status is insufficient. Separate verification does not automatically require another service or another vendor.

The verifier guide must address:

- Correlating an observation with the intended consequence, resource, and selected effect.
- The evidence needed for a positive binding claim.
- The evidence needed for `NO_BIND`, including delayed completion and consistency limits.
- Why a missing record, empty read, or transient failure can be inconclusive.
- Re-observation without issuing the operation again.

Provide focused adapter/verifier contract tests with the reference implementations. A general plugin framework and the full CAGE TestKit remain later releases.

## 12. Reference integrations and flagship examples

Ship all three examples. Each demonstrates evaluation, custody, execution, verification, Effect, and Warrant using local, disposable data.

| Example | Proposed local target | What it teaches |
| --- | --- | --- |
| `database.delete` — lead Quickstart | Temporary SQLite fixture using the Python standard library | Protect a destructive change and observe target state through a separate verification read |
| `access.grant` | Small local access-record fixture | Enforce the permitted resource and grant scope, including a narrowed decision |
| `payment.release` | Simulated local payment ledger | Distinguish acknowledgement from established effect and reconcile uncertainty |

These are reference designs, not production database, IAM, or payment integrations. Fixture choices can be adjusted during API design without changing the core or adding production dependencies.

Where a claimed outcome needs operation correlation or completion evidence, the fixture must provide it. A verifier should not infer that this operation succeeded solely because an unrelated target state happens to match.

The examples must work against the installed distribution, run without credentials or accounts, and document setup and cleanup. No live payments, real access grants, or deletion of user data are part of the default examples.

## 13. Portable Warrant representation

v0.7 introduces a documented, versioned JSON representation for supported Warrant data, together with export and detached inspection/structural validation.

The contract must preserve applicable identifiers, Decision and Effect distinctions, proof references, uncertainty, and lineage. Where lineage references external records, readers must distinguish unresolved references from included records rather than claiming a complete history.

Required behavior:

- Use an explicit format version separate from the package version.
- Preserve the meaning of released fields across v0.7 patch releases; incompatible representation changes require an explicit format-version change and migration guidance.
- Specify required and optional information, enum representations, and compatibility rules in the later schema design.
- Reject malformed data and unsupported format versions with actionable errors.
- Handle supported values explicitly; do not silently stringify arbitrary Python objects or dump private object attributes.
- Preserve supported information through export and readback into the inspection representation.
- Document what is included, omitted, sensitive, or redacted.
- Avoid exporting credentials or arbitrary business payloads by default.
- Treat imported data as untrusted descriptive data, never as authorization to execute.

This is a portability contract. It does not provide cryptographic canonicalization, signatures, independent authenticity, or tamper evidence. Structural validation cannot verify the truth of an external business effect. Those distinctions must be clear in documentation and CLI output.

If redaction removes information needed to assess lineage or a claim, the resulting view must disclose that limitation. Do not silently present a partial view as a complete Warrant.

## 14. CLI and Studio scope

The CLI foundation has four responsibilities: help/version reporting, running the disposable reference examples, inspecting portable Warrants, and checking their structural validity.

Document exit codes and distinguish command/format errors from CAGE lifecycle states. A valid Warrant containing `EFFECT_UNKNOWN` must display that uncertainty clearly. Structural validation must not be named or described as cryptographic or external-effect verification.

Exact commands are decided in the API design. v0.7 does not need a daemon, production operation runner, deployment manager, credentials store, cloud account, or full `cage test` system.

CAGE Studio is optional after required release gates are satisfied. If included, keep it to local inspection of public result/Warrant representations. The runtime must not depend on Studio, and Studio cannot become the only way to inspect an Effect or understand lineage.

## 15. Documentation and packaging

Required documentation:

- Quickstart with prerequisites, installation, one complete action, expected output, and cleanup.
- Lifecycle explanation, including uncertainty and reconciliation.
- Supported API reference and import map.
- Adapter guide and verifier guide.
- Error and failure guide, including what to do after an uncertain execution.
- Low-level semantic API guide.
- Portable Warrant format and inspection guide.
- CLI reference, examples, compatibility statement, and migration notes.
- Security/trust boundaries and integration responsibilities.

Retain the declared Python minimum of 3.11 unless a concrete dependency requirement is separately justified. Publish the actual tested Python and operating-system matrix. Include the user's Windows/PowerShell environment in documentation and verification.

Keep production dependencies minimal. Each added dependency needs a demonstrated requirement and an explicit review; a facade alone is not sufficient reason to add a framework.

Build and clean-install the release wheel. Verify package metadata, public imports, CLI entry points, packaged example resources, and documentation commands from an environment that cannot accidentally import the source checkout.

Making the repository public is a separate launch decision. Before that decision, verify LICENSE, SECURITY.md, CONTRIBUTING.md, CHANGELOG, release documentation, dependency review, repository history, provenance, and governance. v0.7 design approval does not authorize changing repository visibility or publishing a package.

## 16. Security and operability requirements

Security comes from preserving the control boundaries, exposing their limits, and avoiding convenience bypasses.

- Preserve the capability scope of `consequence_id`, `action_type`, and `resource_id` and all existing custody checks.
- Preserve selected-effect integrity from evaluation through execution and verification.
- Never automatically retry execution after timeout, missing acknowledgement, or uncertainty.
- Keep reconciliation observation-only.
- Avoid sensitive payloads and credentials in default diagnostics, examples, and exports.
- Keep runtime operation account-free and telemetry-free in v0.7.
- Validate portable input without evaluating code or restoring executable authority.
- Expose identifiers and actionable diagnostics at each stage.
- Document state ownership, lifetime, concurrency assumptions, and actual recovery limits.

The integration trust model must identify the responsibilities of the application, adapter, verifier, and target system. An application can bypass a library if it still has an unguarded execution path; a malicious extension can misrepresent its own behavior. CAGE integration guidance must explain these boundaries without claiming enforcement the runtime does not provide.

No new distributed lock service, scheduler, durable store, or global exactly-once guarantee is introduced in this release. Existing guarantees remain subject to their documented scope.

## 18. Compatibility and test strategy

The new facade is additive. Existing supported v0.6 behavior, states, custody rules, verification mappings, and lineage semantics remain regression requirements. Any unavoidable compatibility change requires a separately reviewed reason and migration guidance.

Testing must cover behavior at the public boundary rather than simply mirror wrapper implementation:

- Compare representative facade outcomes with the existing low-level lifecycle.
- Exercise every Decision eligibility category, including narrowed-effect propagation.
- Exercise acknowledgement, rejection, errors, lost acknowledgements, and inconclusive verification without unsafe Effect inference.
- Demonstrate reconciliation preserves lineage and invokes no adapter execution.
- Check identity generation, overrides, and conflicting reuse within supported history scope.
- Check capability mismatches and invalid inputs fail before external execution.
- Exercise public imports, configuration, exceptions, and reference extension contracts.
- Validate portable data, supported readback, malformed input, unknown versions, and partial lineage.
- Execute all flagship examples and CLI workflows from a clean wheel installation.

For each meaningful implementation change, use the agreed workflow: focused tests, full regression suite, diff and status review, then a meaningful commit and push before the next feature. Architecture-only drafting does not establish a new passing test count.

## 20. Next design step

Review this architecture first. Then inspect the existing v0.6 source and design the exact public API against its real contracts.

That design must settle:

- Supported exports and compatibility mapping.
- Facade inputs, outputs, ownership, and stage boundaries.
- Identity overrides and state/history lifetime.
- Required configuration and dependency ownership.
- Typed result and exception contracts.
- Adapter/verifier integration points.
- Portable Warrant schema and CLI commands.

The API review must include a proposed happy-path Quickstart and an uncertain-effect/reconciliation walkthrough. Any design that requires developers to rebuild their application around CAGE should be simplified before implementation.

The acceptance standard remains: **“I added CAGE to my architecture.”**
